标题：自建 AI 知识库：从 Obsidian 到本地 RAG 全流程实战记录

标签：#Obsidian #RAG, #LocalLLM, #DevOps, #AIEngineering

我花了三个月时间折腾了一套完全本地的 AI 知识库，起因是公司的数据合规要求加上云 API 的 Token 成本实在太高。我的硬件底座是一台二手 RTX 3090（24GB）配 64G DDR5 内存的主机，操作系统 Ubuntu 22.04 LTS。

很多人问我为什么不用云端？实测下来，如果每天需要处理超过 10MB 的文档检索，云端的费用比电费还贵。而且一旦涉及内部架构设计图、用户隐私数据，上公有链（Public Cloud）本身就是个风险点。所以我决定把 RAG（Retrieval-Augmented Generation）拉回本地跑起来。

第一步：Obsidian 的数据接入与索引策略

我一开始以为 Obsidian 自带插件能直接做向量检索，结果踩了个大坑。官方自带的 `AI Search` 插件依赖外部 API，一旦断网或者配置不对就搜不到东西；社区版的 `Omnisearch` 虽然本地运行但速度极慢，200 个文件索引一次要跑半天，而且经常把 Obsidian UI 卡死在加载圈。

我最终放弃了直接嵌入 Obsidian 插件的方案，选择用 Python 脚本定期同步到向量数据库。Obsidian 的 `.obsidian` 文件夹是加密且敏感的，不能乱动配置。我在项目根目录外建了一个 `docs_index` 目录，通过 Git Hook 监听代码提交（如果文档在 git repo）或者手动触发一个 Shell 脚本来抓取 Markdown 文件。

这里的关键配置是文本切片器（Text Splitter）。我最初用了默认的 `CharacterTextSplitter`，结果检索时经常切断了关键的技术参数定义，导致模型生成答案时逻辑不通。后来切换到 LangChain 的 `RecursiveCharacterTextSplitter`，并自定义了分隔符：

from langchain.text_splitter import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(
    separators=["\n\n", "\n", " ", ""], # 增加段落敏感度
    chunk_size=1024, 
    chunk_overlap=50,
    length_function=len,
)

```

实测数据对比：使用 `bge-m3` 模型进行 Embedding，在测试集上（我随机抽取了 50 个技术文档片段）的检索准确率从最初的 68% 提升到了 92%。但代价是 CPU 占用率飙升到 140%，显存几乎占满。

第二步：向量数据库选型与部署

很多人推荐 Milvus，但我发现对于个人开发者来说，Milvus 的配置复杂度太高了（需要 Docker Compose + Zookeeper）。我最终选了 `ChromaDB`，因为它对 Python API 支持最好且能直接跑在内存里。不过要注意版本兼容性，我用的是 Chroma v0.4.13，LangChain 的旧版接口不支持新版库，导致报错：

# ❌ 错误示例 (v0.5+)
collection.add(...)

```

修正后的 Docker Compose 配置如下（这是我在服务器上实际跑起来的）：

version: '3'
services:
  chroma-db:
    image: ghcr.io/chroma-ai/chroma:v0.4.18 # 锁定版本防止 API 变更
    volumes:
      - ./chromadb:/usr/src/app/data
    ports:
      - "8000:8000"

```

部署后，我通过 Ollama 的 Embedding Model `nomic-embed-text` 进行向量化。这里有个坑：如果你用 Llama3 做生成模型，一定要确保 Embedding 模型和 Generation 模型的架构尽量匹配，否则语义对齐会出问题。我用的是 `bge-m3:latest`（0.15GB）配合 `llama3:8b-instruct-q4_0`（2.7GB）。

第三步：RAG 检索链路调试与性能瓶颈

这是最痛苦的部分。我写了一个简单的 Python FastAPI 服务来对接 Obsidian 的文件目录，实现“搜索 -> 召回 -> 生成”的闭环。

1. Query Processing：

用户输入的问题先经过一个轻量级 LLM（如 `gemma:2b`）进行改写和简化，去除口语化废话。这一步能减少主模型的 Token 消耗。实测后，Token 用量减少了约 30%，生成速度提升了 45%。

2. Retrieval (Top-K)：

我设置了 Top K=3（检索前 3 段），而不是默认的 Top 10。为什么？因为本地显存有限，如果一次拉取太多上下文，Llama-8B 的推理延迟会指数级上升。实测发现：当 Context Window > 4k tokens 时，首字生成时间（TTFT）从 2.5s 飙升到 15s。

配置参数示例：

   retriever = vector_store.as_retriever(
       search_type="similarity_score_threshold", 
       score_threshold=0.7 # 过滤低质量切片，避免幻觉
   )
   chain.invoke(query)

```

3. Generation：

使用 Ollama API 调用本地模型。我配置了 `temperature: 0`（强制确定性），并开启了 `num_predict: 512` 限制输出长度。如果允许无限生成，模型会开始胡言乱语地凑字数。

实测数据对比：云端 vs 自建

为了验证这套方案是否值得折腾，我做了为期一周的 A/B Test。

  • A 组（Cloud API）： 使用 Azure OpenAI GPT-3.5-turbo + LangChain。成本约 $0.1/次查询。平均响应时间 80ms。但检索到的文档片段经常是“幻觉”数据，因为云端索引是基于公共知识库的，无法精准匹配我本地的私有笔记。
  • B 组（本地 RAG）： RTX 3090 + Ollama + ChromaDB。硬件折旧成本忽略不计（电费约 $1/天）。平均响应时间 4.2s（首字生成后流式输出，总耗时取决于模型大小）。检索准确率在私有文档测试集上达到 85%。

    • 踩坑总结：为什么本地 RAG 依然有门槛？

    虽然成本省了，但体验并没有完全超越云端 API。

    1. 显存溢出（OOM）： 当 Obsidian 里的笔记超过 20GB，分片索引时 ChromaDB 的内存占用会瞬间爆满。我后来加了个 `docker run --memory="8g"` 限制，配合异步写入机制才稳住。

    2. 模型幻觉依旧存在： 本地小模型（如 Llama-3-8B）在逻辑推理上远不如 GPT-4o。如果你问复杂的系统架构设计问题，它依然会一本正经地胡说八道。我不得不加了一个“自我修正”的 Prompt：`"Please verify if the retrieved context contains specific details before answering."`

    3. 维护成本： 这不是买软件就能用的。你需要懂 Python、Docker、向量数据库原理。如果哪天 `bge-m3` 更新了接口，你得自己改代码；如果是云端 API，你只需要调个 Key。

    最终配置清单与命令速查

    如果你也想动手搞这套流程，这是我在生产环境（Production）里跑通的 Docker Compose 完整文件：

    services:
  ollama:
    image: ollama/ollama:latest # v0.1.32+
    volumes:
      - ./models:/root/.ollama
    ports:
      - "11434:11434"
  
  chroma:
    image: ghcr.io/chroma-ai/chroma:v0.4.18
    environment: 
      CHROMA_DB_PATH: /data
  
  rrag-api: # Python FastAPI Service
    build: ./app
    ports:
      - "5000:5000"

    ```

    运行后，Obsidian 侧通过本地 HTTP API (`http://localhost:5000/search`) 发送查询请求。我写了一个 Obsidian Plugin (TypeScript) 来封装这个调用：

    // obsidian-plugin-ai-search.ts
async function searchDocs(query: string): Promise<string> {
    const response = await fetch('http://host.docker.internal:5000/search', {
        method: 'POST',
        body: JSON.stringify({ query, top_k: 3 })
    });
    return (await response.json()).answer; // 返回 Markdown 格式的答案
}

    ```

    结论：谁该做这件事？

    如果你是个人开发者、独立研究员，或者公司有严格的内网数据隔离要求，自建 RAG 是绝对值得的。哪怕只是省了 Token 钱，一年下来也是好几万美金（按企业级用量算）。但如果你需要处理复杂的数学推理或代码生成任务，目前本地小模型还是不够用，建议混合部署：简单查询走云端 API，敏感文档检索走本地向量库。

    这套方案我跑了三个月没挂过机，Obsidian 插件稳定同步了超过 500 个 Markdown 文件，索引耗时控制在 30s 以内。如果你不想折腾 Docker Compose，可以直接用 `AnythingLLM Desktop` 的开源版，但记得把数据路径指向你的 Obsidian Vault，这样能省掉写 Python 脚本的时间。

    最后提醒一句：本地 AI 不是魔法。它只是把你的文档变成了向量索引，检索质量依然取决于你如何清洗和分片数据。别指望它能替代人类思考，但它能让你在搜索时不再翻遍几百个笔记文件了。
