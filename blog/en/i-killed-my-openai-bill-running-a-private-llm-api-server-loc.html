I Killed My OpenAI Bill: Running a Private LLM API Server Locally on an RTX 3090

Title: I Killed My OpenAI Bill: Running a Private LLM API Server Locally on an RTX 3090

Tags: #LLM-Inference, #DevOps, #CostOptimization, #Ollama, #RAG

I stopped paying $50/month for GPT-4 access last week. I bought a used NVIDIA RTX 3090 ($620) and spun up an Ollama instance on my home server. Now I have a private API that costs me nothing per token after the hardware depreciation, but it’s not all smooth sailing. This is how I built a local LLM inference endpoint to replace OpenAI without breaking my bank account or losing data privacy.

The Hardware Reality Check: Don't Lie About VRAM

Most tutorials say "just run Ollama." That works until you hit the context window limit and your GPU memory crashes. My setup is an Ubuntu 22.04 LTS server with a single RTX 3090 (24GB VRAM). I didn’t use cloud GPUs because they charge per second ($0.15/hr for A10G), which adds up fast if you run inference continuously.

I started by installing Ollama via their official script, but quickly realized the default quantization (`q8_0`) was too heavy for my VRAM budget during high concurrency. I switched to `q4_K_M` (GGUF format) using llama.cpp backend logic inside Docker:

docker run -d \
  --gpus all \
  -v ~/ollama:/root/.ollama \
  -p 11434:11434 \
  ollama/llama3.2:1b-instruct-q4_K_M

```

Performance Data: On this hardware, `q8_0` hit ~6 tokens/sec but OOM'd at context > 2k. Switching to `q4_K_M` dropped throughput to ~15 tokens/second, which is fine for internal tools but terrible compared to OpenAI’s GPT-3.5 (approx 100+ tps). I accepted the latency trade-off because privacy matters more than speed in my use case, and it saved me from paying $2 per million input tokens.

Building a Proxy Layer: The FastAPI Wrapper

You cannot expose Ollama directly to your frontend; you need an API gateway that mimics OpenAI’s `/v1/chat/completions` schema so existing codebases don't break. I wrote a simple Python wrapper using `fastapi`. This is critical because if you hardcode the model path in every service, migrating models later becomes painful.

from fastapi import FastAPI, HTTPException
import requests

app = FastAPI()

OLLAMA_URL = "http://localhost:11434/api/generate" # Ollama endpoint

@app.post("/v1/chat/completions")
async def chat_completions(request_body):
    try:
        response = requests.post(
            f"{OLLAMA_URL}", 
            json={
                "model": request_body.get("model"),
                "messages": [{"role": m["role"], "content": m["content"]} for m in request_body.get("messages", [])],
                "stream": False, # Non-streaming first to simplify latency measurement
            }
        )
    except Exception as e:
        raise HTTPException(status_code=502, detail="Local model inference failed")

    return {
        "id": response.json()["response_id"],
        "choices": [{"message": {"content": response.json().get("response", "")}}}],
        "usage": {} # Ollama doesn't report tokens used like OpenAI does yet. I added a counter manually via regex later.
    }

```

Lesson Learned: The first version crashed when the context window exceeded 4096 tokens because Ollama defaults to `num_ctx` based on VRAM usage estimation, not explicit configuration. I had to edit `/usr/share/ollama/.config/systemd/user-ollama.service.d/environment.conf` manually or pass flags via Docker run command:

OLLAMA_NUM_CTX=8192 ollama serve llama3.2:7b-instruct-q4_K_M

```

This configuration is mandatory for RAG (Retrieval Augmented Generation) workloads where you need to ingest long documents without truncation errors. Without this flag, the model hallucinates or repeats itself because it runs out of memory mid-stream.

The "Pitfall" of Context Management: Memory Leaks

I hit a major wall during testing on Tuesday morning. I ran `ollama serve` with 128k context window (via experimental patch). It worked for the first request, then started swapping to disk aggressively after 5 minutes.

The Error Log:

[ERROR] [core] GPU memory usage: 94% -> OOM KILL
[INFO] Swapping model weights to CPU... Estimated wait time: 120s

```

I wasted three hours debugging why the server hung when I tried to run a batch of five documents. The issue was not just VRAM but CPU swap. My SSD is fast, but swapping GPU tensors back and forth kills throughput completely.

Fix: I restricted `num_ctx` strictly based on available memory using this formula:

`(VRAM_GB - 4) * (16 / num_layers)` roughly. For my RTX 3090 (24GB), that meant a hard cap of 8k tokens. Anything beyond required external chunking logic in Python before sending to the model, not inside Ollama itself.

Benchmarking: Local vs OpenAI

I ran `speed_eval` against both endpoints for identical prompts over 1 minute intervals. Here are the real numbers from my local machine (RTX 3090) compared to OpenAI's GPT-4o-mini API pricing ($0.15/million tokens).

| Metric | Local Ollama (q4_K_M) | OpenAI API (GPT-4o-mini) |

| :--- | :--- | :--- |

| Latency (TTFT) | 800ms - 1200ms | ~350ms |

| Throughput | 12 tokens/sec sustained | 60+ tokens/sec burst |

| Cost per M Tokens | $0.00 (Amortized) | $0.15 / month at scale |

| Privacy Risk | None (Data stays on disk) | High (Logs sent to Azure/US) |

I also tested vLLM as an alternative backend because it supports continuous batching, which Ollama lacks by default. I built a Docker container with `vllm/vllm-openai` image:

docker run -d --gpus all \
  -e VLLM_MODEL=meta-llama/Llama-3-8B-Instruct \
  vllm:v0.2.1 /bin/bash -c "python examples/openai_chat.py"

```

Result: vLLM was 5x faster than Ollama (60 tokens/sec vs 12), but it required a Python environment setup that took me another day to debug CUDA compatibility issues (`libcuda.so.1` missing). For my use case, I stuck with Ollama because the deployment script is one-liner and easier for DevOps teams who don't want `pip install vllm`.

Reliability: Systemd Watchdog & Docker Restart

Running inference locally isn’t just about startup; it’s about uptime. My server rebooted once during a power surge, killing my Ollama process. I didn't rely on the OS to restart it automatically because GPU drivers sometimes hang in `nvidia-smi` state after crash.

I implemented a systemd watchdog service that monitors `/proc/net/dev` for network activity (Ollama exposes status via HTTP) and kills/restarts if unresponsive:

[Unit]
Description=Watchdog Service for Ollama API Gateway
After=docker.service
Requires=docker.service

[Service]
ExecStartPre=/bin/sh -c 'docker ps | grep ollama || docker start ollama'
Restart=always
RestartSec=10s

```

This simple config saved me from manual intervention. Without it, I would have lost access to the API for 2-3 minutes during every reboot cycle until `ollama serve` was manually triggered again. The cost of downtime in production is higher than hardware maintenance costs.

When You Should Stop and Switch Back

I’m not saying local inference replaces OpenAI everywhere. If you need 10k tokens context (like long-form legal documents) or sub-200ms latency, the RTX 3090 becomes a bottleneck regardless of quantization level. I tested `Llama-3-70B` on my single GPU and it crashed instantly even with FP8 quantization.

At that point, you must switch to cloud inference providers like RunPod or Lambda Labs ($0.25/hr for A10G). But the ROI calculation changes:

  • Local (Self-hosted): Cheaper if usage < 1M tokens/month per month after hardware depreciation (~$3/day equivalent cost of GPU power + electricity).
  • Cloud API: Better when you need burst capacity. You pay for what you use, but at $0.5/hr on A10G, running idle is a waste compared to paying OpenAI's fixed rate ($2/mo per 4k tokens roughly).

    • Final Verdict: Is It Worth It?

    Yes, if privacy and cost are your primary drivers. No, if latency is critical for user experience or you need massive context windows beyond 8k without chunking logic. I am currently running this on a home server with `docker compose` orchestration to manage the whole stack (Ollama + FastAPI Proxy).

    Here is my final Docker Compose file that keeps everything consistent:

    version: '3'
services:
  ollama:
    image: ollama/ollama:latest
    volumes:
      - ./models:/root/.ollama/models
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]

  api-proxy:
    build: . # Local python folder with requirements.txt
    ports: ["8000:8000"]
    environment:
      - OLLAMA_BASE_URL=http://ollama:11434/api/generate

    ```

    I have saved $60/month compared to my previous OpenAI bill, but I lost 5x speed. That trade-off is acceptable for internal documentation tools and code assistants where human latency tolerance (waiting a few seconds) exists. If you deploy this in production without monitoring GPU memory usage (`nvidia-smi --query-gpu=memory.used`), expect it to crash during peak load spikes from batch requests.

    One last warning: Do not trust the model weights on disk as permanent backups. I lost my fine-tuned `mistral-7b-instruct-v0.2-q4_k_m.gguf` file once when Docker container was deleted by mistake (`docker rm -f`). Always keep a backup of your quantized models in S3 or local storage outside the volume mount path, because Ollama stores them as `.gguf` files inside `/root/.ollama/models`, and if you don't persist that correctly, you lose everything.

    This setup works for me right now on an old laptop with 24GB RAM (CPU inference via `llama.cpp`). It’s slower (~1 token/sec) but it runs without a GPU driver at all. If I need more speed, I’ll upgrade to the A6000 next month when prices drop below $800. Until then, this local stack keeps my data private and costs me nothing per request beyond electricity bills ($5/month for 24/7 uptime).
