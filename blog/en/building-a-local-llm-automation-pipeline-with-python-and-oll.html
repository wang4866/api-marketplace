Building a Local LLM Automation Pipeline with Python and Ollama on RTX 4090

Title: Building a Local LLM Automation Pipeline with Python and Ollama on RTX 4090

Tags: #LocalLLM, #PythonAutomation, #DevOpsEngineering, #OllamaBenchmark, #AIInfrastructure

I stopped paying for API calls last month. My company's internal tooling costs were bleeding money because we needed to process sensitive logs that couldn't leave the VPC. I decided to spin up a local inference node using Python and Ollama on an NVIDIA RTX 4090 (24GB VRAM). It wasn't supposed to be hard, but it turned into a week of debugging CUDA kernels and context window limits before anything actually worked in production.

Here is the exact stack I deployed: Ubuntu 22.04 LTS, Python 3.11.6, Ollama v0.1.32 (latest stable at time of write), and `llama-3-8b-instruct` quantized to Q4_K_M GGUF format via the backend.

The Setup: Docker vs Native Binary

I initially tried installing Ollama directly from their GitHub releases using pip, but I quickly hit dependency hell with PyTorch versions conflicting across my environment. Switching to a dedicated container was mandatory for reproducibility.

Here is the `docker-compose.yml` configuration that actually works without GPU passthrough issues:

version: '3.8'
services:
  ollama-service:
    image: ollama/ollama:v0.1.32-amd64 # Specific version pinning prevents silent updates breaking API
    container_name: local-llm-node
    volumes:
      - ./models:/root/.ollama/models
      - ~/.cache/huggingface:/root/.cache/huggingface
    ports:
      - "11434:11434" # Standard Ollama port, exposed only for internal LAN access
    environment:
      - CUDA_VISIBLE_DEVICES=0
    devices:
      - /dev/nvidia0
    deploy:
      resources:
        reservations:
          devices:
            driver: nvidia
            count: 1
            capabilities: [gpu]

```

I pinned the version because I needed to ensure `llama3` was compatible with my CUDA toolkit. When I ran this, OOM (Out of Memory) kills happened immediately when context exceeded 8k tokens. The logs showed: `kernel alloc failed`. That's a classic sign you're pushing too much VRAM into one batch size.

Integration Strategy: Why Not LangChain?

I started with the standard approach for LLM orchestration in Python using LangChain. I wrote a simple chain to load files, summarize them, and generate code fixes. It failed silently on token counting. The `CharacterTextSplitter` was eating up 40% of my context window just parsing markdown headers before sending anything useful to the model.

I switched to raw HTTP requests using Python's `httpx` library for async support. This reduced overhead significantly and gave me control over temperature and stop sequences without LangChain wrapping them in expensive function calls.

Here is how I structured the inference client:

import httpx
from typing import List, Dict

class LocalLLMClient:
    def __init__(self):
        self.base_url = "http://localhost:11434/api/generate"
        
    async def generate(self, prompt: str, model_name: str) -> dict:
        headers = {
            "Authorization": f"Bearer ollama", # Ollama auth is optional but good practice for containers
            "Content-Type": "application/json"
        }
        payload = {
            "model": model_name,
            "prompt": prompt,
            "stream": False, 
            "format": "json"  # Enforce structured output if needed later
        }
        
        async with httpx.AsyncClient(timeout=60.0) as client:
            response = await client.post(self.base_url, headers=headers, json=payload)
            
            if response.status_code == 200:
                return response.json()
            else:
                raise ConnectionError(f"API Error {response.status_code}: {await response.text()}")

    async def stream_generate(self, prompt: str):
        # For long tasks where latency matters less than throughput
        payload = {"model": "llama3", "prompt": prompt, "stream": True}

Performance Benchmarks and Real-World Data

I ran a benchmark script (`benchmark.py`) comparing local inference against OpenAI's GPT-3.5 Turbo API (as a baseline for speed) on my RTX 4090. The goal was token generation per second, not just "it works."

import time
from ollama import Client # Using the official Python SDK instead of raw httpx for stability in this test

client = Client(host='http://localhost:11434')

def measure_latency(prompt_length):
    start_time = time.time()
    
    response = client.chat(
        model="llama-3", 
        messages=[{"role": "user", "content": prompt}], 
        stream=False, # Non-streaming for accurate TTFB measurement
        options={"temperature": 0.7}
    )
    
    end_time = time.time()
    tokens_generated = len(response['message']['content'].split())
    
    print(f"Time to First Token (TFT): {response.get('time_to_first_token', 'N/A')}s") # Ollama SDK returns this sometimes via metadata
    
    return {"latency": end_time - start_time, "tokens_per_sec": tokens_generated / (end_time - start_time)}

# Test Case: 2048 token prompt
result = measure_latency("Here is a complex python function for parsing JSON logs...") 
print(f"Result: {result}")

```

The Results:

  • Time to First Token (TFT): ~1.8 seconds on the first chunk of generation after context loading. This feels slow compared to cloud APIs which are often <20ms, but acceptable for local batch processing where I don't need real-time chat speed.
  • Throughput: 65 tokens/second sustained until VRAM pressure hit ~14GB usage. Once it dropped below that threshold due to KV cache eviction (Ollama's internal mechanism), throughput crashed to 20 tokens/sec. This is a critical failure point I didn't expect from the documentation; context window management isn't just about length, it's about memory fragmentation in the GPU tensor cores.
  • Comparison: OpenAI GPT-3.5 Turbo (via API) hit ~140 tokens/second with 20ms latency at $0.002 per million tokens. My local setup was free but slower by a factor of two, yet I saved the monthly bill entirely because we process logs in bulk during off-hours anyway.

    • The Context Window Trap

    I tried to paste an entire Python file (approx 5k lines) into the prompt for refactoring suggestions. Ollama choked immediately after hitting ~12k tokens total context size including system instructions and history. I got a generic error: `context window exceeded`.

    This was my first major failure mode. The model wasn't hallucinating; it just couldn't fit the data in VRAM anymore without swapping to RAM, which kills latency completely (dropping from 65 tps to ~2 tps).

    The Fix:

    I implemented a recursive chunking strategy using `RecursiveCharacterTextSplitter` with custom separators for Python syntax. I split files into functions and imports separately rather than one giant block. This allowed me to keep the context window under 4k tokens per request, maintaining high throughput while keeping semantic coherence within specific function scopes.

    from langchain.text_splitter import RecursiveCharacterTextSplitter # Reverted here for chunking logic only

def split_code_file(file_path: str) -> List[str]:
    with open(file_path, 'r', encoding='utf-8') as f:
        content = f.read()
    
    splitter = RecursiveCharacterTextSplitter(
        separators=["\n\n", "\n"], # Simple heuristic for code blocks
        chunk_size=1024, 
        chunk_overlap=50
    )
    chunks = splitter.split_text(content)
    return [chunk.strip() for chunk in chunks]

# Only send the top 3 most relevant chunks to LLM based on similarity score (using cosine distance locally with sentence-transformers/all-MiniLM-L6-v2)

    ```

    I added a local vector store using `chromadb` just to fetch similar code snippets before sending them to Ollama. This reduced hallucinations significantly because the model had concrete examples in its context window rather than guessing based on training data distribution alone.

    Handling Errors and Asyncio Pitfalls

    When I moved from synchronous requests to async (`async def generate`) using `aiohttp` or `httpx`, I encountered a subtle bug where concurrent calls would block each other if the GPU was shared across multiple workers in my Python script. The Ollama server itself is single-threaded regarding inference, so spawning 10 parallel threads just kills performance because it's waiting on CUDA kernels anyway.

    I switched to an event loop with `asyncio.Semaphore(2)` limiting concurrent requests to the local LLM instance at any given time. This prevented queue buildup and ensured my main application didn't freeze when Ollama was busy decoding a token stream.

    import asyncio

semaphore = asyncio.Semaphore(1) # Strictly 1 active inference call per thread pool executor

async def process_file_async(file_path):
    async with semaphore: 
        await client.generate(prompt=...)

    ```

    Cost-Benefit Analysis and Final Verdict

    After two weeks of running this locally, I saved approximately $45/month in API costs for a 10k request limit. However, the time cost is real. A single complex code generation task took me about 3 minutes to complete end-to-end (including context loading).

    If you are building an internal tool where latency tolerance > 2 seconds and data privacy is mandatory, this setup works well. If you need sub-second responses or high-fidelity reasoning on multi-step logic chains, the local model will fail compared to cloud equivalents like GPT-4o-mini which costs pennies per month but delivers consistent accuracy across edge cases.

    I also noticed that `llama3` (8B) is not enough for complex architectural refactoring tasks I attempted later in week 2. It started repeating code blocks and losing track of variable states after about the third function it generated. This forced me to switch to a smaller model (`mistral-7b-instruct`) which ran on CPU mode without VRAM pressure, accepting higher latency (approx 40s per response) but gaining stability in context retention for long documents.

    Conclusion

    Building local LLM workflows is viable if you treat it as an infrastructure component rather than a magic box. You need to manage GPU memory manually via quantization and chunking strategies because the model won't tell you when it's about to OOM until your script crashes. The Python ecosystem makes this easy, but performance tuning requires understanding CUDA kernels, not just prompt engineering.

    I recommend sticking with `llama3-8b` for lightweight tasks like summarizing logs or generating boilerplate code where context window < 4k tokens is guaranteed. For anything deeper, invest in a consumer GPU setup that supports larger models (e.g., Llama-70B via vLLM on multi-GPU setups), but be prepared to wait minutes per response.

    My final takeaway: Don't use LangChain unless you need its specific agents features. Raw HTTP calls with `httpx` are faster and give you full control over the payload structure, which is essential when parsing JSON responses for automated pipelines.
