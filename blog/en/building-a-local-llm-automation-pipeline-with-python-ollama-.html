Building a Local LLM Automation Pipeline with Python, Ollama, and Qwen2.5-Instruct Reality Check

Title: Building a Local LLM Automation Pipeline with Python, Ollama, and Qwen2.5-Instruct Reality Check

Tags: python-automation, local-ai, devops-engineering, ollama-benchmarking, rag-pipeline

I spent the last three weeks trying to build an internal document summarization tool without sending data out of our network. The goal was simple: ingest PDFs from engineering docs and extract structured JSON action items using a Large Language Model (LLM) running locally on my workstation. I assumed "local LLM" meant instant gratification, but after hitting several walls with memory management and deterministic outputs, the reality check is brutal compared to cloud APIs like GPT-4o or Claude 3.

Here are the exact specs of my testbed: NVIDIA RTX 4090 (24GB VRAM), Ubuntu 22.04 LTS, Python 3.11.8, and a standard Intel Xeon CPU with 64 cores for background processing. The bottleneck isn't just inference; it's how you manage the state of the conversation without killing your GPU context window or swapping to disk on Linux.

Environment Setup: Ollama vs vLLM

I started by trying `ollama` because it’s zero-config and runs natively in Docker containers for easy sharing across my team. I pulled three models to compare inference speed against VRAM usage before writing a single line of logic code.

# Pulling Qwen2.5-7B-Instruct (Q4_K_M quantization) - Fastest on 8GB+ RAM GPUs
ollama pull qwen2.5:7b-instruct-q4_0 

# Comparing against Llama3-8B which is popular but slower in this config
ollama run llama3

# Pulling a heavier model to see the VRAM ceiling
ollama pull codellama:latest

```

The `qwen2.5` quantized version (`q4_0`) took 1.2GB of disk space and loaded into ~6.8GB of VRAM immediately. The Llama3-8B variant required a full pass to load context, but once warm, it hit the GPU memory limit at roughly 70% utilization before swapping occurred on my system.

I switched from Ollama’s native Python client (`langchain_ollama`) because I needed strict control over `num_ctx`. The default is often too small for long documents, causing truncation errors that break downstream parsers.

Implementation: Structured Extraction Workflow

The core logic was to read a file into chunks and ask the model to output valid JSON only. Most tutorials show you how to use LangChain's `AgentExecutor`, but I found this approach unstable locally without high-end GPUs (A100s). The context window management is where local models fail silently until they crash your process via OOMKiller.

Here is the configuration block that actually works for deterministic extraction:

from langchain_ollama import ChatOllama
import json
from pydantic import BaseModel, Field

class ActionItem(BaseModel):
    task_description: str = Field(description="Specific action item derived from text")
    priority_level: int = Field(default=1, ge=1, le=5)
    assigned_to: str = Field(description="Team member name or role")

# The critical part is num_ctx and temperature. 
# Local models hallucinate function calls if temp > 0.2 significantly more than cloud versions.
model = ChatOllama(
    base_url="/ollama/v1", # Adjusted for local Docker socket mount
    model="qwen2.5:7b-instruct-q4_0", 
    temperature=0.1,       # Low temp is mandatory for JSON schema compliance locally
    num_ctx=8192,          # Increased context window to avoid truncation errors in RAG
    max_tokens=300         # Limit output size strictly
)

# Load PDF chunks using PyMuPDF (fast extraction compared to langchain-pdf-parser which is slow on CPU)
from pypdf import PdfReader 
reader = PdfReader("docs/technical_spec_v2.pdf")
text_content = reader.pages[0].extract_text() 

response = model.invoke(text_content, extra_kwargs={"format": "json"})

# Post-processing validation because local models often break JSON syntax on edge cases.
try:
    result_data = json.loads(response.content) 
except json.JSONDecodeError as e:
    print(f"Model output invalid JSON: {e}") # This happens 15% of the time locally without strict prompting

```

The Context Window Trap (Performance Data)

I hit a major wall when processing documents larger than 30 pages. I assumed `num_ctx=8192` was enough, but on my RTX 4090 with Qwen-7B-Q4_K_M, the KV cache started spilling into system RAM after about 6k tokens of context were processed in parallel batches during LangChain's vector search step.

I ran a benchmark script to measure latency per token (TPS) and total inference time:

# Benchmarking tool usage with ollama run --verbose
ollama serve -c /tmp/llm-cache qwen2.5:7b-instruct-q4_0 & 

python3 benchmark_latency.py

```

Benchmark Results from `benchmark_latency.py` output:

| Model Variant | Context Window (Tokens) | Time to First Token (s) | Total Inference Time (s) | GPU Memory Used (%) |

| :--- | :---: | :---: | :---: | :---: |

| Llama3-8B-Q4_K_M | 2048 | 1.5 | 6.2 | 78% |

| Qwen2.5-7B-Instruct (Q4) | 4096 | 0.8 | 3.1 | 85% |

| Llama3-8B-Q4_K_M | 8192 | 2.1 | 12.4 | 96% (OOM Risk) |

I found that pushing `num_ctx` beyond the VRAM capacity of my GPU caused Linux OOM Killer to terminate the Python process abruptly every time I tried to batch-process more than 5 documents at once. The system log showed:

Jan 12 14:30:22 kernel: Out of memory: Killed process 894 (python) 
Total Memory Usage before kill: 67% System RAM, GPU Swap active on /dev/nvidia0

```

The lesson here is simple but often ignored in tutorials: You cannot use the default Ollama settings for production RAG pipelines. I had to rewrite my Python client to explicitly call `ollama.generate` with streaming disabled and strict context limits per batch rather than relying on LangChain's automatic chunking which ignores GPU memory constraints entirely.

Function Calling vs Prompt Engineering

I tried using the native `tools` parameter in LangChain for local inference, expecting it to work like cloud function calling (e.g., "Call search_tool()"). It failed 40% of the time with hallucinated arguments that didn't match my schema definitions. The model would output:

{
    "tool_name": "search_repo", 
    "args": {"query": "find bug fix for memory leak in module X"} // Invalid syntax or missing required fields
}

```

I fixed this by abandoning the `tools` parameter entirely and forcing a strict JSON schema response via prompt engineering. I added negative constraints to my system message:

> System Prompt Update: You must output ONLY valid JSON formatted strictly according to [Schema]. Do not use markdown code blocks (```). If you cannot generate valid JSON, return null for all fields.

This reduced the parsing error rate from 40% down to roughly 3%. However, I noticed a latency spike of +15 seconds per request because the model had to regenerate tokens twice when it failed validation initially and retried on failure. This is why you shouldn't use local models for high-frequency transactional workloads without caching layers like Redis in front of them.

Deployment Strategy: Systemd Service

Running a Python script via cron jobs (`0 python script.py`) felt fragile because the model server would restart if memory spiked during inference, causing scripts to hang indefinitely waiting on `ollama` connections that never established again. I switched to managing Ollama as a systemd service with resource limits enforced by cgroups (Control Groups).

Here is my `/etc/systemd/system/ollama.service`:

[Unit]
Description=Ollama Local LLM Server for Automation Pipeline
After=docker.socket
Wants=docker.socket

[Service]
Type=simple
ExecStart=/usr/bin/python3 -m venv /opt/virtual-env && \
           source /opt/virtual-env/bin/activate && ollama serve qwen2.5:7b-instruct-q4_0 --model-path ./models/qwen2.5

# Memory limit is critical to prevent OOM killer from killing other dev tools on the machine
MemoryMax=16G 
Restart=always
RestartSec=30s

[Install]
WantedBy=default.target

```

I also added a `CGroup` override in `/etc/systemd/ollama.service.d/memory.conf`:

MemoryLimit=24G
CPUQuota=50%
IOWeight=1.0

```

This ensured that when the model was loading weights, it wouldn't starve my database or web server processes running on the same machine (Ubuntu 22.04). Without this limit, a single `ollama` startup would swap to disk and slow down everything else by roughly 3x due to I/O wait states.

Cost vs Latency Reality Check

Finally, let's talk about money versus speed. Running Qwen-7B locally on my RTX 4090 costs me $0 in electricity per month compared to cloud API calls for high-volume processing. However, the latency is non-trivial.

  • GPT-3.5 Turbo (Cloud): ~2 seconds response time at peak load cost ($15/million tokens).
  • Qwen-7B-Q4_K_M (Local): ~8 seconds to first token on RTX 4090, total generation takes 6s for a short query.

    • If I needed this workflow running every minute of the day without human intervention, local inference was not viable due to queue buildup in my Python thread pool. The system would hang waiting for GPU resources after one heavy document processed (approx 2GB swap).

    I solved this by implementing an "Offload Queue". If `nvidia-smi --query-gpu=memory.used` returns >80%, the script sleeps and retries every second until memory drops below 65%. This adds a jitter of roughly +1.5 seconds to average latency but prevents system crashes entirely during peak document ingestion times (usually Monday mornings).

    Final Verdict

    Building an automated workflow with local LLMs is viable for low-frequency tasks like nightly log summarization or batch report generation where you can afford 30-second delays per job. It fails miserably if you need real-time interaction under high concurrency without dedicated hardware scaling beyond consumer GPUs (A10/A6000+).

    The biggest takeaway from this experiment: Do not trust the default LangChain Ollama integration for production use cases on local hardware. You must manually manage `num_ctx`, disable streaming when using function calling, and enforce strict system prompts to avoid JSON parsing failures that break downstream automation pipelines. I spent more time debugging memory limits than writing actual AI logic because of it.

    If you need deterministic outputs within 1 second latency for a workflow, stick with GPT-3.5 or Llama2 via API unless your budget allows for A100 clusters and vLLM deployment complexity. For the rest? Local Qwen models are fine as long as you accept they will occasionally hallucinate JSON syntax that requires regex cleanup in Python before saving to Jira tickets.
