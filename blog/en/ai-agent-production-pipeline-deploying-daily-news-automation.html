AI Agent Production Pipeline: Deploying Daily News Automation with OpenHermes and LangGraph

Title: AI Agent Production Pipeline: Deploying Daily News Automation with OpenHermes and LangGraph

Tags: [AI Agents, DevOps, LLM Engineering, Content Generation]

I built a content generation pipeline last month using the Hermes model stack wrapped in an agentic workflow. It was supposed to be simple automation for daily blog posts based on RSS feeds. In reality, it turned into a debugging marathon that cost us 40% more compute than expected until we fixed the orchestration layer.

Here is exactly how I architected it, where the money burned out of thin air, and what version numbers actually matter in production.

Architecture Setup: Dockerizing the Brain

I didn't use a managed API endpoint for this. The cost variance between vLLM inference and OpenAI endpoints was too high (3x difference at 7B parameter size). I deployed `openhermes-2.5-mistral-7b` locally on an A10G instance using Docker Compose to keep latency predictable.

Here is the exact deployment configuration that worked for us:

version: '3.9'
services:
  vllm-server:
    image: vllm/vllm-openxlab/openhermes-2.5-mistral-7b:v0.1
    ports:
      - "8000:8000"
    environment:
      VLLM_MODEL_PATH: /models/hermes-v0.4
      MAX_TOKENS_PER_REQUEST: 3000
    deploy:
      resources:
        reservations:
          devices:
            nvidia:
              count: "1"
              capabilities: ["gpu"]

  agent-orchestrator:
    build: ./src/agents
    environment:
      - VLLM_API_URL=http://vllm-server:8000/v1/completions
      - LANGCHAIN_TRACING_V2=true
    depends_on: [vllm-server]

```

The `agent-orchestrator` is a Python script using LangGraph. I pinned the version explicitly because v0.3 introduced breaking changes in state management that broke our retry logic immediately after deployment.

The Agent Logic and Tooling Constraints

I defined three tools: `Searcher`, `Writer`, and `Reviewer`. Most tutorials show generic tool definitions, but they fail when you need strict output formats for downstream parsing. I implemented a JSON schema constraint directly in the prompt template to prevent hallucinated markdown that breaks our ingestion pipeline.

The initial version of the agent definition looked like this:

from langgraph.graph import StateGraph

class HermesAgent(StateGraph):
    def __init__(self, llm_client):
        self.llm = llm_client
    
    # This is where we enforce structure strictly to avoid regex failures downstream
    tools_config = {
        "searcher": {"type": "function", "schema": {...}}, 
        "writer": {"type": "function", "schema": {"output_format": "json"}}
    }

# The loop logic was simple but fragile: search -> write -> review.
workflow = StateGraph(HermesAgent)

```

I found that the model hallucinated tool calls when given ambiguous prompts about current events (e.g., 2024 election news). It tried to "search" a non-existent API endpoint because it didn't know I was using `arxiv` for technical papers but `newsapi.org` for general content.

I fixed this by adding explicit environment variables and modifying the system prompt:

system_prompt = """You are Hermes Agent v2. You must strictly follow tool definitions provided in JSON schema. 
Do not invent tools. If a search fails, return 'NO_DATA' immediately."""

```

Performance Metrics from Real Runs

I ran 50 iterations of the pipeline to measure throughput before hitting production scale. The results were mixed depending on how we handled context windows.

Baseline (Without RAG):

  • Latency: Average 14 seconds per article generation. P99 latency was 32s.
  • Token Usage: ~8,500 tokens per request for a full day's news summary.
  • Cost: $0.006 per article (using vLLM on A10G).

    • After Optimization (Context Window Management):

    We realized the model was wasting compute re-reading previous conversation history in every step of the graph cycle. I switched to a stateless context injection strategy using Redis for vector storage instead of passing full chat history through LangGraph memory nodes.

  • New Latency: Average 6 seconds per article generation. P99 latency dropped to 12s.
  • Token Usage: ~3,500 tokens per request (reduced by 58%).
  • Cost: $0.0027 per article.

    • This is the kind of number that matters for DevOps teams managing GPU budgets. A simple state management change saved us roughly $14/month on our instance bill over a standard month's operation.

    The Hallucination Bug and Why It Happened

    I hit a major pitfall during week 2. We deployed to Kubernetes, but the `Hermes` model started generating code snippets for Python scripts instead of natural language summaries when asked about "implementation details."

    The Error Log:

    stderr: [LangGraph] Agent failed step 'writer': 
Error parsing response from Hermes-7B: JSONDecodeError at line 4. Expected string, got list object.
Traceback (most recent call last):
File "/src/agents/tools.py", line 123, in execute_writer
    data = json.loads(response)

    ```

    The model was confident but wrong about the output format because I didn't enforce a strict temperature setting during inference for tool-calling steps. It defaults to `temperature=0` usually, but LangChain's wrapper sometimes passes higher values by default when streaming responses are enabled.

    The Fix:

    I updated the Docker Compose environment variables and added a post-processing validation step in Python:

    export TEMPERATURE_WRITER_STEP=0.1  # Critical for deterministic tool output
export TEMPERATURE_SEARCH_STEP=0.7   # Higher allowed here, more creative search needed

    ```

    This small config change stopped the JSON parsing errors completely. I also added a `try-except` block in the orchestration layer that catches non-JSON responses and retries with a corrected prompt template containing an explicit error message example (few-shot prompting). This reduced failure rate from 15% to <0.2%.

    Deployment Strategy: Kubernetes vs Docker Compose

    Initially, I tried running this on AWS EKS using Helm charts for the `vllm` deployment because we wanted auto-scaling based on CPU usage. It failed miserably during peak traffic spikes (around 3 PM UTC). The GPU scheduler couldn't keep up with dynamic batch requests due to memory fragmentation in vLLM's default configuration.

    I switched back to Docker Compose for the inference layer and used a simple Python-based load balancer proxy (`uvicorn`) that queues requests when the A10G is saturated, then spins up ephemeral pods via K8s only if queue depth > 5. This hybrid approach cost more in management overhead but saved us from OOMKilled errors during traffic bursts.

    Key Config for Stability:

    # Inference Client Configuration (vLLM)
client = vllm.AsyncEngineClient(
    engine_url="http://localhost:8000/v1", 
    max_batch_size=4,  # Prevents context starvation during batching
    scheduling_policy='lru'
)

    ```

    Cost Analysis and ROI Reality Check

    I need to be honest about the economics. The "AI Agent" hype often ignores inference costs per token when you scale beyond a few hundred requests. We tracked this using our internal billing dashboard integrated with LangSmith.

    Over 30 days, we generated approximately 150 articles (manual + automated).

  • Total Inference Cost: $42.50 USD.

    • Human Writer Equivalent: ~$680 for same volume at standard freelance rates ($4.5/hr 15h/day/30 days = roughly equivalent effort, adjusted for quality variance).

    However, the "quality" metric is where it gets tricky. The automated articles had a higher hallucination rate than human-written pieces in niche topics (e.g., specific financial regulations mentioned without citations). I implemented an external validation step using `googleapis` to verify facts before publishing. If confidence score < 0.85, the article goes to a human review queue via Slack webhook integration.

    # Validation Step Snippet
if agent_response.confidence_score > 0.9:
    publish_to_s3(agent_response)
else:
    send_webhook(slack_channel="human-review-queue", payload=agent_response)

    ```

    This hybrid approach ensures we don't burn money on bad content while keeping the automation pipeline running at scale. Without this validation gate, our error rate would have been 12% of total output volume, which is unacceptable for a public-facing product.

    Final Lessons from Production Ops

    I learned three hard lessons that didn't make it into any tutorial blog post:

    1. Model Versioning Matters: Using `openhermes-2.5` vs the original `mistral-instruct-v0.3` changed how the agent handles function calling syntaxes completely. I had to rewrite all tool definitions when upgrading the model backend just last week due to a breaking change in JSON schema handling. Always pin your exact Docker image tag, not just the library version.

    2. State Management is Expensive: Passing large context windows through LangGraph nodes consumes memory linearly with depth. I capped history retention at 5 turns per agent instance using Redis TTL keys set to `1h`. This prevented OOM errors on our worker pods during concurrent execution tests (concurrent requests = 4).

    3. Latency is Non-Linear: Adding a single validation step increased total pipeline latency from ~6s to ~28s for the first article in a batch, but dropped back down as parallelization kicked in after warmup. I monitored this via Prometheus metrics (`langgraph_agent_duration_seconds`) and set up alerts when p95 > 30s.

    I am not saying AI Agents replace human writers entirely. They are better at fetching data and structuring it into drafts than they are at verifying truthfulness or creative nuance without supervision. The Hermes stack is powerful, but only if you treat the model as a stochastic component in your pipeline that requires strict guardrails, monitoring, and version control—just like any other piece of legacy infrastructure.

    If I were to start this project today, I would skip LangGraph for now and use `crewai` or direct function calling via OpenAI API until we hit 10k RPM throughput requirements where local inference becomes mandatory anyway. But for our current scale (5-20 concurrent users), the Hermes + vLLM setup on A10G is cost-effective enough to justify the maintenance overhead of managing GPU nodes manually instead of paying per-token overage fees from cloud providers who charge 3x more than running it ourselves.
