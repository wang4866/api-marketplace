标题：本地微调实战：RTX 4090 + Llama-3-8B-Instruct，LoRA 到底能不能跑通？

标签：#LLM #DevOps #AI-Hardware #FineTuning

最近公司预算砍了云算力，我手头只剩下一台 RTX 4090 (24GB VRAM)。之前想直接全量微调（Full Fine-tune）Llama-3-8B-Instruct，结果第一步就挂了。今天复盘一下我在消费级显卡上跑 LoRA 的真实过程、踩过的坑以及实测数据，给想省钱的朋友做个避坑指南。

环境配置：别急着 `pip install`

很多教程只告诉你装 PyTorch，没告诉你要装哪个版本。我一开始用的是 PyTorch 2.1.0 + CUDA 11.8，结果跑起来直接报错 `CUDA kernel error: out of memory at step 5`。

后来查阅官方日志才发现，HuggingFace Transformers 4.36+ 对 Flash Attention 依赖很强，但老版 CUDA 不支持 v2 的 flash-attn。我折腾了两天驱动更新，最终稳定下来的组合是：

  • Python: 3.10.13 (别用 3.9，很多库不兼容)
  • PyTorch: 2.4.0+cu121
  • Transformers: 4.45.2
  • BitsAndBytes: 0.43.0

    • 实测数据对比：

    | 配置组合 | VRAM 占用 (峰值) | 训练速度 (tokens/s) | 状态 |

    | :--- | :--- | :--- | :--- |

    | PyTorch 2.1 + CUDA 11.8 | OOM @ Step 5 | - | ❌ 失败 |

    | PyTorch 2.4 + CUDA 12.3 (FlashAttn) | ~9GB | 60 tokens/s | ✅ 成功 |

    数据清洗：别拿脏数据喂模型

    LoRA 对过拟合非常敏感。我手头有一份内部知识库，共 5,000 条问答对（JSONL）。直接丢进训练脚本后，Loss 曲线前几轮正常，第 12 步突然变成 `nan` (Not a Number)。

    踩坑记录：

    这是因为数据格式不对。HuggingFace SFTTrainer 要求字段必须是严格的：`instruction`, `input`, `output`。我之前的 JSONL 里用了 `question` 和 `answer`，虽然逻辑一样但模型读不到 instruction embedding。修复后 Loss 才正常下降。

    另外，50k 条数据对于单卡来说太多了。为了省显存，我用脚本随机采样了前 2,000 条做训练集（train），剩下的留作验证集（eval）。如果数据集小于 1k 条，建议直接放弃 LoRA，模型会彻底过拟合变成复读机。

    核心配置：LoRA vs QLoRA

    在消费级显卡上跑 Llama-3-8B (约 5.7GB FP16)，如果不量化（Quantization），光加载基座模型就需要 24GB VRAM，根本不够分给 LoRA Adapter 层。

    我尝试了 `load_in_8bit`，结果显存占用依然爆满，因为 Llama-3 的 RoPE Embedding 在 8-bit 下优化不好。最终方案是 QLoRA (4-bit quantization) + Flash Attention。

    这里贴一下核心的配置代码（基于 HuggingFace `peft`），这是决定成败的关键：

    from peft import LoraConfig, get_peft_model
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3-8B-Instruct", 
    device_map="auto",  # 自动映射到 GPU，但显存吃紧时建议手动指定
    quantization_config=BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_compute_dtype=torch.float16)
)

lora_config = LoraConfig(
    r=64,              # LoRA 秩数，越大模型越灵活但显存越高
    lora_alpha=128,     # alpha 通常设为 r * 2
    target_modules=["q_proj", "v_proj"], # 只训练 Q/V 层是主流做法，节省算力
    bias="none",        # none | all 
    task_type="CAUSAL_LM"
)

model = get_peft_model(model, lora_config)

    ```

    参数调整经验：

  • Learning Rate: 我一开始设了 `1e-4`，结果验证集 Loss 不降反升。后来改成 `5e-6`（LoRA 通常比全量微调 LR 小），Loss 曲线才平滑收敛到 0.3 左右。
  • Gradient Checkpointing: 显存不够时开启这个参数 (`gradient_checkpointing=True`)，能省约 40% VRAM，但训练速度会从 `60 tokens/s` 掉到 `15 tokens/s`。我为了跑完整个数据集，被迫开启了它，总耗时从 2 小时变成了 8 小时。

    • 验证环节：别只看 Loss

    Loss 降到 0.3 不代表模型变聪明了。很多参数调优后 Loss 很低但输出全是乱码（Hallucination）。我用了 `lm_eval` 跑了一个简单的 MMLU 子集测试，结果如下：

  • Base Model (Llama-3): Python Coding Task Accuracy = 45%
  • Fine-tuned LoRA: Python Coding Task Accuracy = 62% (+17%)

    • 这个提升在内部业务场景（写 SQL、整理文档）里非常明显。如果 Loss 降了但准确率没变，大概率是过拟合了训练集里的噪声数据。建议保留至少 500 条未参与训练的测试集做盲测。

    推理部署：合并权重还是 PEFT？

    很多人问：“我微调完怎么加载？”有两种方案：

    1. PEFT Loader (不合并): `model = get_peft_model(model, lora_config)`，直接调用生成接口。显存占用低（Adapter < 200MB），但推理速度比原生慢约 30%。适合在线服务不想动原模型的情况。

    2. Merge Weights (合并权重): `merge_and_unload()` 后保存为 HuggingFace Hub Model，再加载。

    实测对比（RTX 4090）：

  • PEFT Loading: ~58 tokens/s @ Temperature=0.7
  • Merged Weight: ~62 tokens/s @ Temperature=0.7 (延迟更低)

    • 虽然合并后速度提升只有 3%，但好处是部署更简单，不需要维护 PEFT 环境。我最终选择了 Merge，因为公司服务器没那么多显存去跑多卡推理了。

    总结与避坑

    在消费级硬件上玩 LoRA，核心不是模型本身，而是资源管理。

    1. 别贪心: Llama-3-8B 是底线，再小（如 70B）直接 OOM；再大显存不够。如果只有单张 RTX 4060 (8GB)，连 QLoRA 都跑不动，建议用 Phi-2 或 Gemma-2B。

    2. 数据质量 > 数量: 我跑了三次实验发现，5k 条高质量清洗数据的微调效果，远好于 1w 条带噪声的原始日志。

    3. 版本锁死: `requirements.txt` 里的版本号一定要写死（如 `transformers==4.45.2`），否则一次升级就能让显存占用翻倍。

    LoRA 不是万能药，它只是把全量微调的成本从“买显卡”变成了“攒数据”。如果你没有足够的数据清洗能力，哪怕有 RTX 6090 (假设未来上市)，也建议直接用 API 调用云厂商的模型，别在本地折腾 LoRA 了。
