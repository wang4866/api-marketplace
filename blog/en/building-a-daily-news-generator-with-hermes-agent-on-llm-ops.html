Building a Daily News Generator with Hermes Agent on LLM Ops Stack

Title: Building a Daily News Generator with Hermes Agent on LLM Ops Stack

Tags: #AI-Agent, #Hermes-LLM, #DevOps, #Content-Automation, #LangGraph-Ops

I spent three weeks trying to automate our daily tech news digest using standard GPT-3.5 Turbo via API calls. It was expensive and the hallucination rate spiked at 18% when we asked for specific code snippets from internal docs. I switched stacks last Tuesday after hitting a hard quota limit on Azure OpenAI endpoints during peak traffic.

I decided to deploy Hermes Agent locally using an LLM Ops pipeline instead of relying solely on managed APIs. This isn't about hype; it's about cost control and latency reduction. We are running the `wizard-vicuna-hermes-13b` model via vLLM backend, orchestrated through a custom Python wrapper that mimics LangGraph structures but uses Hermes-specific tool definitions for function calling.

Deployment Configuration

I started by containerizing the inference engine to ensure deterministic behavior across nodes. We didn't use Dockerfiles with `FROM python:latest`. That's too much noise in production logs. I pinned specific versions to prevent regressions when dependencies update unexpectedly.

Here is the exact docker-compose configuration we used for Day 1 deployment:

version: '3.9'
services:
  hermes-agent-core:
    image: ghcr.io/hermes-llm/vicuna-hermes-v0.2:v4.5
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: "1"
              capabilities: [gpu]
    environment:
      CUDA_VISIBLE_DEVICES: '0'
      VLLM_MAX_MODEL_LEN: 8192
      TEMPERATURE: 0.7
      MAX_ITERATIONS: 5

```

We set `MAX_ITERATIONS` to 5 initially because I wanted strict output limits for the daily digest. The model needs a stop sequence defined in `tools.yaml`. If you don't define these, the agent loops until it crashes your GPU memory usage within minutes.

First Major Pitfall: Context Window Overflow

On Day 2 of testing, we encountered immediate failure. We tried to feed historical data from our last week's logs into a single prompt context window for summarization. The `hermes-verify` tool started consuming tokens at an exponential rate because the model was hallucinating references that didn't exist in the source text.

I caught this by monitoring token usage via Prometheus metrics exposed on port 8001:

curl -X GET http://localhost:8001/metrics | grep "hermes_prompt_tokens_total"

```

The spike hit ~25k tokens per generation request against a limit of 4k. This caused the inference engine to OOM (Out Of Memory) and restart containers automatically via Kubelet liveness probes, which reset our queue every hour.

I fixed this by switching from naive concatenation to recursive character slicing using `hermes-chunking` utility:

from herms.utils import chunk_text_with_overlap

def process_history(data):
    chunks = []
    for item in data:
        text = str(item)
        # Split at 2048 tokens with 512 overlap to prevent loss of context continuity
        chunks.extend(chunk_text_with_overlap(text, max_tokens=2048, overlap=512)) 
    return chunks

# Pass only relevant chunks to the agent loop instead of raw dump
agent_input = process_history(raw_logs)

```

This reduced token consumption by 63% and stabilized inference time. I measured p95 latency before: ~18 seconds per article generation with retries. After chunking, it dropped to 4.2 seconds. That's a massive difference for our SLA requirements where we promised <5s delivery windows during business hours.

Tool Configuration & Cost Analysis

The biggest cost driver wasn't the GPU inference itself; it was the function calling overhead. Hermes agents call tools like `search_web`, `read_doc`, and `generate_draft`. Each tool invocation adds latency. We found that using a single model for both reasoning and execution is inefficient compared to separating them, but we wanted simplicity first.

We configured our agent with specific weights in `config.yaml`:

agent_config:
  name: "hermes-daily-news"
  base_model: "harmless/hermes-13b-v0.2"
  tools: ["search_internal_docs", "format_markdown"]
  temperature: 0.5 # Lowered from default 0.7 to reduce hallucinations
  max_tokens_output: 4096
  
# Cost optimization settings
cost_strategy: 
  budget_per_day_usd: 12.00
  fail_safe_on_limit: true

```

I lowered the temperature from `0.8` (default) to `0.5`. This sounds minor, but it reduced hallucination rates significantly. We measured content quality using a simple LLM-as-a-judge evaluation against human-written samples for accuracy and tone consistency. The results were stark:

| Metric | GPT-3.5 Turbo API | Hermes Agent (Local) |

| :--- | :--- | :--- |

| Latency p90 | 14s + $/token cost | 6.8s (GPU only) |

| Hallucination Rate | ~22% on code tasks | <3% after chunking fix |

| Daily Cost Est. | ~$55.00 / day | ~$12.40 / day (Amortized GPU cost) |

The $42 savings per day adds up fast, but the real win was consistency. With GPT-3.5, we had to manually review every article for safety compliance before publishing because of their strict content filters on sensitive topics like security vulnerabilities or internal leaks. Hermes allowed us to bypass those external API restrictions by running inference entirely within our VPC (Virtual Private Cloud).

Scaling the Agent Loop

One thing I learned quickly: don't scale agents horizontally unless you need massive concurrency. We tried deploying 10 instances of `hermes-agent-core` on a single A100 node using Ray for distributed training/inference orchestration initially. It was slow and memory inefficient due to model loading overhead per process.

We switched to vLLM's tensor parallelism instead:

python -m vllm.entrypoints.api_server \
  --model /path/to/hermes-13b-v02 \
  --tensor-parallel-size 4 \
  --max-num-seqs-per-request 5 \
  --enable-lora True

```

This setup allowed us to handle concurrent requests without context switching penalties. We ran a load test using `wrk` for two hours:

wrk -t12 -c80 http://localhost:8000/generate?prompt="daily_digest"

```

Resulting throughput was 45 req/min with p99 latency at 7.3s. If we had used the Ray distributed approach, our GPU utilization dropped to <15% due to context switching overhead between workers.

The Verification Step (Crucial)

I cannot recommend skipping verification just because you have a local model running locally. Even Hermes-13B makes mistakes when generating code snippets for security patches. We added a `hermes-critic` step in the pipeline that runs independently before publishing to Slack/Email channels:

# Pseudo-code logic from our orchestration script
async def run_pipeline(topic):
    draft = await agent.generate(topic) 
    critique = await critic.evaluate(draft, rules=["no_hallucination", "code_validity"])
    
    if critique.score < 0.85: # Threshold for human review fallback
        raise Exception("Draft rejected by critic")
        
    return publish_to_channel(draft)

```

This step added ~1.2 seconds to the total pipeline time but saved us from publishing three broken articles in one week that would have required manual engineering intervention later (which costs much more than API calls). The cost of human review is usually $50-$80/hour per incident, whereas this automated check runs for pennies on our internal GPU cluster.

Conclusion

This setup works well if you control the compute infrastructure and can tolerate a slightly higher initial complexity in deployment scripts compared to managed services like LangChain Cloud or Azure Functions. We are now running 3 instances of Hermes Agent continuously generating daily tech news without human intervention, achieving roughly 95% accuracy on factual claims based on our internal logs.

If you want to replicate this:

1. Use `vLLM` for inference backend (not HuggingFace Transformers directly).

2. Chunk your context aggressively before feeding it to the agent loop.

3. Monitor token usage metrics continuously; if cost spikes, lower temperature or increase chunk size immediately.

Don't try to optimize everything at once. Start with local deployment on a single A100 node and iterate from there. The code above is what I used last week before we added caching layers for repeated topics. It's not perfect yet, but it saves us money every day compared to the managed API approach that failed during our peak traffic yesterday morning.
