Fine-Tuning LLMs Locally with LoRA: A Real-World Guide for Consumer GPUs

Title: Fine-Tuning LLMs Locally with LoRA: A Real-World Guide for Consumer GPUs

Tags: #LLM-FineTuning, #LoRA, #NVIDIA-GPU, #DevOps-Pipeline, #AI-Inference

I stopped buying cloud credits last month. My budget didn't allow it anymore. I decided to fine-tune a model locally on my workstation instead of renting an A100 instance for $7/hour. The hardware is consumer-grade: two NVIDIA RTX 3090s, each with 24GB VRAM, connected via NVLink (or PCIe if you're unlucky like me). I wanted to build a coding assistant specific to our internal stack without paying enterprise fees.

Here's the reality check before we start writing any code. You cannot fine-tune Llama-3-8B in full precision on consumer hardware. It will OOM immediately. The only way is QLoRA (Quantized Low-Rank Adaptation). I spent three days debugging memory fragmentation issues just to get a single epoch running without crashing the CUDA kernel context.

Environment Setup: Versioning Matters More Than You Think

Most tutorials say "install transformers". They don't mention which versions of `torch` and `cuda` you need, or why your training crashes silently after 5 minutes. I learned this when my first run hit a silent OOM during the validation step. The GPU was fine; PyTorch had lost track of allocated memory blocks due to mixed precision mismatches.

Here is exactly what worked for me on Ubuntu 22.04 with an NVIDIA driver version `535.183.01`. I pinned my dependencies because upgrading CUDA from 11.7 to 12.1 broke the backward compatibility of some older HuggingFace modules unless you rebuild everything from scratch.

conda create -n lora-finetune python=3.9.16 -y
source activate lora-finetune
pip install torch==2.0.1 torchvision==0.15.2 --index-url https://download.pytorch.org/whl/cu118
pip install peft transformers accelerate bitsandbytes datasets trl sentencepiece protobuf

```

I used `cu118` for PyTorch 2.0 because I found that newer CUDA versions (12.x) caused a memory leak in the gradient checkpointing logic when using `bitsandbytes`. The performance hit was negligible, but stability improved by roughly 40% on my dual-GPU setup compared to trying to force CuDNN8 compatibility with PyTorch nightly builds.

Configuring LoRA: Rank and Alpha are Not Arbitrary Numbers

You will see tutorials suggesting `r=16` or `rank=32`. I tested this against the 4-bit quantization of Llama-3-8B on my single RTX 3090 first, then moved to dual cards for better throughput. The memory usage scales linearly with rank size until you hit VRAM limits where fragmentation kills performance.

I used `lora_config.yaml` instead of passing arguments directly because it allows me to version control the hyperparameters without cluttering my training script. Here is the config I settled on after profiling:

r: 64
target_modules: ["q_proj", "k_proj", "v_proj", "o_proj"]
lora_alpha: 128
dropout: 0.05
bias: "none"
use_gradient_checkpointing: true
gradient_accumulation_steps: 4
learning_rate: 2e-4
per_device_train_batch_size: 1

```

I set `r=64` and `lora_alpha=128`. Why? Because on a single card, I could only afford to train with rank 32. When I bumped it to 64 using two GPUs (splitting the load), inference quality improved by roughly 5% perplexity-wise compared to base models, but training time doubled due to communication overhead between devices via NCCL.

The `use_gradient_checkpointing: true` flag is non-negotiable here. Without it, I was hitting OOM errors during the forward pass on every batch because PyTorch tries to cache activations for backpropagation by default in full precision mode. With QLoRA and 4-bit quantization (`load_in_8bit=False`, `use_qlora=True`), memory usage drops significantly.

The Training Pipeline: Data Loading Bottlenecks

I used the HuggingFace datasets library to load my proprietary dataset (50k examples of code generation tasks). However, I encountered a classic pitfall during data preprocessing. If you don't tokenize before saving or use `map` without caching properly, your disk IO becomes the bottleneck rather than GPU compute.

from transformers import AutoTokenizer
import datasets

dataset = datasets.load_dataset("json", data_files="data/train.json")["train"]
tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-3-8B-Instruct")

def preprocess(example):
    text = example['prompt'] + '\n' + example['completion']
    return tokenizer(text, truncation=True, max_length=2048)

dataset = dataset.map(preprocess, batched=False)  # Warning: False here is slow but safe for small datasets

```

I switched to `batched=True` and added a `.cache_file()` call. This reduced data loading time from ~15 minutes per epoch down to under 30 seconds on my NVMe SSD (Samsung PM981). The dataset size matters immensely; I found that training beyond 2 epochs with only 5k samples leads to overfitting where the model starts repeating patterns rather than learning new syntax.

Running the Command: What Actually Happens in `accelerate`?

I used HuggingFace's Trainer wrapped inside an Accelerate launcher because it handles distributed data parallel (DDP) better for multi-GPU setups without writing custom collators manually. Here is the exact command I executed to start training on two GPUs with mixed precision enabled:

accelerate launch \
  --num_processes=2 \
  train.py \
  --model_name_or_path meta-llama/Llama-3-8B-Instruct \
  --dataset_config data/train.json \
  --lora_r 64 \
  --learning_rate 2e-4 \
  --per_device_train_batch_size=1 \
  --gradient_accumulation_steps=4 \
  --output_dir ./checkpoints/llama3-lora-v1 \
  --fp16 False

```

Wait, I initially used `--fp16 True`. That was my mistake. On consumer hardware with mixed precision (BF16), the optimizer state is too heavy for VRAM even if weights are quantized. Switching to FP32 math operations in the forward pass (`bf16=False` or standard float) increased training stability but reduced throughput by 50%. I settled on `fp16=True` with a learning rate of `2e-4`, which is higher than what you'd see for full fine-tuning.

The "NaN Loss" Incident: A Real Debugging Log

After two epochs, my loss curve spiked to infinity and the process crashed. This happened because I didn't configure a proper warmup schedule in the optimizer configuration file (`optimizer_config.yaml`). PyTorch's default AdamW doesn't handle sudden high gradients well when learning rates are aggressive on small datasets.

I added this snippet to `training_args.py` before restarting:

max_grad_norm=1.0, 
lr_scheduler_type="cosine",
warmup_ratio=0.05  # Added this after debugging the NaN spike

```

This fix stabilized training immediately. The loss curve dropped smoothly from 3.2 to 2.8 over five epochs without exploding gradients again. I also noticed that validation steps were taking longer than expected because of `eval_strategy="no"`. When you set it to "epoch", your GPU sits idle during the forward pass while waiting for CPU-side tokenization, which kills throughput on multi-GPU setups where communication overhead dominates compute time.

Inference Speed and Quality: The Real Numbers Matter

Training is useless if inference is slow. I converted my fine-tuned adapter into a GGUF format using `llama.cpp` because it's significantly faster than the HuggingFace Transformers pipeline for local execution. Here are the benchmarks from my dual RTX 3090 setup (24GB + 24GB):

| Model Variant | Quantization Format | Latency (First Token) | Throughput (Tokens/s) | Memory Usage (VRAM) |

| :--- | :--- | :--- | :--- | :--- |

| Llama-3-8B Base | Q4_K_M.gguf | 120ms | 65 tokens/sec | ~19GB per GPU |

| LoRA Fine-Tuned (v1) | Q4_0 + Adapter | 135ms | 72 tokens/sec | ~19.8GB total |

The fine-tuned model is slightly slower to start because the adapter adds a tiny overhead, but throughput increases by roughly 10%. This matters for interactive coding tools where latency > 100ms feels sluggish to users. However, I noticed that on my single RTX 4090 (24GB), inference was faster than dual-3090s because of the PCIe bus bottleneck when splitting weights across two cards in LoRA mode.

Deployment: Dockerizing for Portability

I didn't just leave it as a Python script. I containerized everything so my team could spin up instances without fighting dependency hell on their machines. Here is the `Dockerfile` snippet that worked after fixing CUDA version mismatches inside containers (which always happens):

FROM nvcr.io/nvidia/pytorch:23.10-py3
RUN pip install peft transformers accelerate bitsandbytes datasets trl sentencepiece protobuf
COPY ./checkpoints/llama3-lora-v1 /app/model
CMD ["python", "inference.py"]

```

I had to pin the PyTorch version inside Docker because `pip` tries to upgrade everything by default, which breaks compatibility with the base image's CUDA runtime. I also added an `.env` file for API keys and model paths so no secrets end up in git history or logs.

Lessons Learned from Failure Modes

1. Don't trust tutorial defaults: The `lora_alpha=2*r` rule of thumb is good, but on small datasets (under 5k examples), I found that lowering alpha to match rank (`alpha=r`) prevents overfitting significantly better than doubling it.

2. Validation kills throughput: If you don't have a separate validation set or if your dataset is too large for full evaluation every epoch, disable eval entirely during training and do manual sampling later using `llama.cpp`. It saves massive amounts of GPU time.

3. Quantization isn't just about saving VRAM: Using Q4_K_M quantization instead of FP16 adapters makes the model smaller (2GB vs 50MB adapter size) but slightly less expressive on edge cases like math-heavy queries compared to full LoRA rank-128 models.

Final Thoughts: Is This Worth It?

Yes, if you need a specific domain adaptation and cannot afford cloud compute for weeks of training. My total cost was the electricity bill (approx $0.50/hour) plus my time debugging NCCL errors on two GPUs. I saved roughly 8 hours compared to renting an A10G instance via Lambda Labs or RunPod, which would have taken me about a week just to get stable weights due to queue times and spot instances getting killed mid-training run.

If you are starting this project today: Start with QLoRA on one card (24GB+). Use `r=64`. If OOMs occur during validation, reduce batch size or enable gradient checkpointing (`use_gradient_checkpointing=True`). Do not use full precision fine-tuning unless your budget allows for 80GB of VRAM.

I'm currently pushing the rank to 128 on my dual-3090 setup next week to see if I can squeeze out more performance without hitting memory fragmentation again. Until then, this pipeline handles our internal documentation queries reliably enough that we stopped paying for a generic LLM API subscription entirely.
