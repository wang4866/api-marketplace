Fine-tuning LLaMA-2-7B on an RTX 4090 with LoRA: A DevOps Engineer's Guide

Title: Fine-tuning LLaMA-2-7B on an RTX 4090 with LoRA: A DevOps Engineer's Guide

Tags: #LLM, #LoRA, #DevOps, #AI-Hardware, #FineTuning

I bought a consumer-grade NVIDIA GeForce RTX 4090 (24GB VRAM) last month. My expectation was to run enterprise-level LLM inference locally without cloud costs. Reality hit me hard within the first week of training: I could not fit even one batch on my GPU using full fine-tuning. The memory allocator threw a CUDA Out Of Memory error immediately at step 0. That is where this post starts—not with hype, but with how to actually get weights onto disk without paying for an A100 cluster.

I am going to show you exactly what I did to fit LLaMA-2-7B into my hardware using Low-Rank Adaptation (LoRA). This isn't a theoretical walkthrough; it's the exact configuration that survived three failed training runs on my local machine before producing usable weights for production inference.

Environment Setup: Version Locking is Mandatory

When I started, I used `pip install transformers peft accelerate bitsandbytes`. That generic command led to version conflicts within 48 hours because of a known issue in PyTorch 2.3 with the PEFT library's adapter merging logic on certain CUDA versions.

I pinned my environment explicitly:

python=3.10.12
torch==2.2.0
peft==0.7.0.dev45
transformers==4.38.0
accelerate>=0.26.0

```

Why 2.2? Version 2.3 introduced a change in how `bfloat16` is handled on consumer GPUs that caused NaN losses during the first epoch for me. I stuck to FP16 mixed precision with manual gradient scaling instead of relying solely on automatic AMP, which often crashes when the optimizer state exceeds VRAM limits.

I containerized this using Docker to ensure reproducibility across different machines in my team's lab:

FROM pytorch/pytorch:2.2-cuda12.1-cudnn8-runtime
RUN pip install transformers peft accelerate bitsandbytes datasets
COPY requirements.txt . && pip install -r requirements.txt --no-cache-dir
CMD ["python", "train.py"]

```

The LoRA Configuration: Why Rank 8?

The most common mistake I see in tutorials is setting `lora_rank` to 16 or 32 without understanding the memory overhead. On an RTX 4090, you have roughly 7GB of usable VRAM after accounting for PyTorch's allocator and system processes when training a 7B model.

I configured my adapter using this YAML file (`config.yaml`):

r: 8
lora_alpha: 16
target_modules: ["q_proj", "v_proj"]
bias: none
dropout: 0.05
modules_to_save: null
use_gradient_checkpointing: true
torch_dtype: torch.float16
max_seq_length: 2048
per_device_train_batch_size: 1
gradient_accumulation_steps: 16
learning_rate: 2e-4
num_epochs: 3

```

Memory Math: A full fine-tune of LLaMA-7B requires roughly 15GB just for the optimizer states (AdamW) plus weights. With `r=8`, I only update ~0.6% of parameters, keeping trainable params low enough to fit in FP16 precision without exploding gradients. If I had set `lora_alpha` too high relative to rank without adjusting dropout or learning rate, my validation loss spiked immediately at epoch 2 due to overfitting on the small dataset (5k examples).

I enabled gradient checkpointing (`use_gradient_checkpointing: true`). This trades compute for memory by recomputing activations during backprop. Without this flag, I hit OOM after step 100 with `batch_size=4`. Enabling it allowed me to double my effective batch size without crashing the GPU process.

The Training Command and First Crash

I didn't use a notebook environment because they lack resource monitoring for production-grade debugging. I ran this command from my terminal:

accelerate launch \
  --config_file accelerate_config.yaml \
  train.py \
  --model_name_or_path meta-llama/Llama-2-7b-hf \
  --dataset_type alpaca \
  --output_dir ./lora_4090_run1

```

The `accelerate` config file (`accelerate_config.yaml`) is critical. I set the device map to `"auto"` but manually forced mixed precision:

compute_environment: LOCAL_MACHINE
mixed_precision: fp16
num_cpu_threads_per_process: 8
gpu_ids: [0] # Force specific GPU if multi-GPU setup exists
ramp_up_batch_size: true

```

The First Crash: In my first attempt, I set `per_device_train_batch_size` to 2. The system threw a CUDA OOM error at step 15/30 because the optimizer state for LoRA adapters is still significant compared to full fine-tuning on small cards. I fixed this by switching to `batch_size=1` and increasing `gradient_accumulation_steps` from 8 to 64. This effectively simulated a batch size of 2 but split it across two steps, reducing peak memory usage per step while maintaining the same total gradient update frequency.

Hyperparameter Tuning: Learning Rate Sensitivity

I tried learning rates starting at 1e-3 and quickly saw loss divergence (NaNs). I dropped to 5e-4 for epoch 1, then fine-tuned down to 2e-4 for epochs 2 and 3. This decay strategy was necessary because the model converged too fast on the training set but failed to generalize when evaluated against a held-out test set of 50 prompts generated by LLM eval scripts.

I also had to adjust `warmup_ratio` from default (0.1) down to 0.03. The standard warm-up caused instability in early steps where gradients were too noisy for the small LoRA adapters. I found that without a longer linear warmup, the loss curve looked like an inverted 'L' shape instead of smooth decay.

Evaluation: Did It Actually Learn?

After training finished (approx 18 hours wall-clock time), I needed to verify if this was just memorization or actual learning. I used `lm_eval` locally with a simple script, not relying on the HuggingFace Trainer's built-in evaluation which can be flaky due to token truncation issues in some datasets.

I compared three checkpoints:

1. Base Model: LLaMA-2-7B (No LoRA)

2. LoRA Rank 8: My config above (`r=8`)

3. Full Fine-Tune Attempted on CPU: I tried running full fine-tuning using QLoRA quantization to fit in RAM, but it was too slow for daily iteration cycles (1 epoch took 4 days).

Performance Data from `lm_eval` run:

  • Base Model Perplexity: ~23.5
  • My LoRA-8 Model Perplexity: ~26.0 on the validation set of complex reasoning prompts.
  • Latency (Tokens/sec): Base model inference took 14 tokens/second locally with `llama.cpp`. My fine-tuned version dropped to 9 tokens/second due to adapter overhead, but accuracy improved by roughly 5% on coding benchmarks compared to the base weights.

    • Wait, that latency drop was annoying for my use case. I switched to merging LoRA adapters into the main model before inference using `peft.merge_and_save`. This reduced the VRAM requirement from ~12GB (unmerged) to ~9GB (merged), but increased training time by 30% during fine-tuning because we had to compute gradients for all layers.

    The Overfitting Trap I Hit Twice

    I encountered a classic issue at epoch 4 where validation loss started climbing while train loss kept dropping linearly. This is the hallmark of overfitting on small datasets (5k examples). My initial `weight_decay` was set too low (0.01). When I bumped it to 0.2, regularization increased enough to stop memorizing noise in my dataset.

    I also noticed that using a larger rank (`r=32`) caused the model to hallucinate more aggressively on out-of-distribution queries compared to `r=8`. The higher capacity adapter learned patterns specific to the training data rather than general reasoning capabilities. This trade-off is critical: if you need speed, use low-rank adapters; if you need accuracy and have VRAM headroom, increase rank but expect longer epochs (roughly 10% more per epoch for `r=32` vs `r=8`).

    Inference Pipeline Optimization

    Once I had the final merged weights (`lora_4090_run3_merged.safetensors`), I moved to serving. Using HuggingFace Transformers directly was too slow (15ms/prompt latency). I switched to `vLLM` for inference, but vLLM defaults often struggle with quantized LoRA models unless configured correctly.

    I used a specific config file in the deployment script:

    from transformers import AutoModelForCausalLM, AutoTokenizer
model = AutoModelForCausalLM.from_pretrained("path/to/merged", torch_dtype=torch.float16)
tokenizer = AutoTokenizer.from_pretrained(path_to_tokenizer)
# ... load into device 0 and start serving with vLLM backend for async requests

    ```

    I measured throughput on my local machine:

  • Base Model: ~25 tokens/sec (FP16).
  • LoRA Merged: ~38 tokens/sec. The merged model is slightly faster than the base because it doesn't have to load separate adapter weights into memory, just standard dense layers with adjusted biases and linear projections during forward pass.

    • Conclusion: What Actually Works on Consumer Hardware?

    I tested this setup against three other configurations in my lab (RTX 3090s). The RTX 4090 consistently outperformed the older cards by roughly 15% in training speed due to faster CUDA cores, but memory bandwidth was still a bottleneck. If you have less than 24GB VRAM on your consumer card, do not attempt LLaMA-7B fine-tuning with `batch_size > 1` without gradient accumulation or QLoRA quantization (bitsandbytes).

    The key takeaway from my failures: Do not trust default hyperparameters. Every dataset has different noise levels. If you are training on code data, increase dropout to 0.2 and reduce learning rate by half compared to natural language tasks. I spent three days debugging why the model was outputting random characters; it turned out `max_seq_length` in my config file wasn't matching the actual truncation logic in the dataset loader.

    This guide is not a promise of state-of-the-art results, but a working baseline for deploying custom models locally without cloud costs. If you follow these exact numbers and commands, I guarantee you will avoid the OOM crashes that wasted my last two weekends on this project.
