CPU 量化推理的可行性报告

标题：无需 GPU 跑 AI:CPU 量化推理的可行性报告

标签：#AI 部署 #DevOps #LLM #性能优化

上周公司预算被砍，原本计划采购 A800 显卡做本地知识库检索的方案直接黄了。作为负责 Infra 的我，当时第一反应是“这活没法干”，但后来在内部技术分享会上听到后端同事说他们把 Llama-3-8B 跑在了纯 CPU 上，我才决定亲自测一下。别买显卡了：我在纯 CPU 服务器上跑通了量化推理

说实话，刚上手的时候我心里没底。以前做模型部署，大家默认都是 CUDA + TensorRT，一旦没有 GPU，我就觉得性能会崩盘到不可用级别。为了验证这个假设，我找了一台内部闲置的测试机，配置如下：

  • CPU: Intel Xeon Platinum 8269CY (32 vCPU)
  • RAM: 128 GB DDR4 ECC Memory
  • OS: Ubuntu 22.04 LTS

    • 没有 GPU 的情况下，我对比了三种方案：原生 PyTorch CPU、ONNX Runtime + INT8 Quantization、以及目前最火的 Ollama (GGUF)。

    踩的第一个坑：线程数设置不对，CPU 跑不动

    很多人以为量化推理就是直接 `python main.py` 就能快起来，结果我实测发现完全不是这么回事。在 Linux 环境下，默认的多进程调度效率极低。

    我用原生 PyTorch CPU 跑了个 Hello World（ResNet-50），延迟是毫秒级的；但换成 Llama-3-8B (FP16) 时，首字生成时间（TTFT）直接飙到了 4.2s，吞吐量只有 0.9 tokens/s。这显然没法用。

    后来我意识到问题出在 OpenBLAS 和 MKL 的线程竞争上。默认配置下，32 核 CPU 被强行分成了几十个线程去抢内存带宽，导致上下文切换频繁。我在 `~/.bashrc` 里加了环境变量：

    export OMP_NUM_THREADS=16
export OPENBLAS_NUM_THREADS=8
export MKL_NUM_THREADS=4

    ```

    重启服务后，PyTorch CPU 的 TTFT 降到了 2.5s，但这依然是 FP16。为了进一步压榨性能，我必须上量化模型。

    方案对比：Ollama vs ONNX Runtime (INT8)

    这里有个关键数据点：FP16 在 CPU 上的推理速度几乎可以忽略不计。我测试了两种量化路径。

    路径一：ONNX Runtime + INT8 Quantization

    这是传统 DevOps 最熟悉的路径。我先用 `torch.onnx.export` 导出模型，再用 ONNX-ML 进行动态量化（Dynamic Axis）。配置如下：

    import torch
from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained("meta-llama/Meta-Llama-3.1-8B", device_map="cpu")
# 手动加载 INT8 quantization config (简化示意)
config = model.config.to_dict()

    ```

    导出 ONNX 后，使用 `onnxruntime` 推理。实测数据：在 32 vCPU 下，INT8 量化后的 TTFT 约为 1.8s，生成速度 4.5 tokens/s。

    路径二：Ollama + GGUF (Q4_K_M)

    这是目前社区最推荐的 CPU 方案。我直接在 Docker 里拉取了 Ollama 镜像 `ollama/ollama:0.3`，并指定了量化模型 `qwen2-7b-instruct-q4_0.gguf`（注：为了测试方便选的是 Qwen 小参数，8B 在 CPU 上显存压力太大）。

    Docker run 命令如下：

    docker run -d \
    --name ollama-cpu-test \
    -p 11434:11434 \
    -e OLLAMA_NUM_PARALLEL=20 \
    -v /mnt/data:/root/.ollama \
    ollama/ollama:latest \
    serve --model qwen2-7b-instruct-q4_0.gguf --num_ctx 16384 --threads 32

    ```

    实测数据对比（同一台机器，连续跑 5 次取平均）：

    | 方案 | Model Size (Params) | Quantization Type | TTFT (s) | Generation Speed (tokens/s) | RAM Usage (Peak) |

    | :--- | :--- | :--- | :---: | :---: | :---: |

    | PyTorch CPU | Llama-3 8B | FP16 | 4.20s | 0.95 tokens/s | ~7GB (Swap Heavy) |

    | ONNX Runtime INT8 | Llama-3 8B | INT8 | 1.85s | 4.5 tokens/s | ~8GB |

    | Ollama GGUF Q4_0 | Llama-2 7B (Q4) | Quantized | 1.6s | 9.2 tokens/s | ~6GB |

    > 注：ONNX Runtime INT8 的转换成本极高，一次导出耗时约 30 分钟。Ollama GGUF 是预量化的，直接下载就能跑，但 Q4_0 精度损失比 FP16 大一些（BLEU score 下降约 5%）。

    遇到的第二个坑：内存交换导致的“假死”

    在测试过程中，我遇到了一个非常典型的 DevOps 问题：Swap。

    虽然机器有 128GB RAM，但模型加载时如果上下文窗口（Context Window）开得太大，或者并发请求多，CPU 的虚拟地址空间就会耗尽。Linux 默认会开启 Swap，导致磁盘 I/O 飙升。

    我监控了 `iostat`：

    # 运行前 iowait = 0%
# 推理中 iowait = 85%, CPU Utilization = 12%

    ```

    系统负载（Load Average）瞬间变成 4.3，但实际计算能力没跑满。这是因为量化后的模型虽然显存需求低，但在 CPU RAM 上依然吃紧，一旦触发 Swap，速度直接掉到 0.5 tokens/s。

    解决办法很简单：限制并发和上下文长度。在 Ollama 配置里加上 `--num_ctx` 参数（默认是 4k），并且设置 Docker 的内存上限 `/etc/docker/daemon.json`:

    {
    "default-runtime": "nvidia", 
    "runtimes": { ... },
    "memory-swappiness": -1, // 禁止 Swap，如果物理内存够用的话
    "oom_kill_disable": true 
}

    ```

    结论：什么时候该用 CPU？

    跑完这一轮测试，我整理了一份内部决策表。如果你正在评估是否要上 GPU，或者预算有限必须走纯 CPU 路线，请参考以下数据支撑你的决定。

    1. 适用场景：

  • 非实时交互任务：比如日志分析、离线文档摘要（RAG），对延迟不敏感（TTFT > 2s）。
  • 小模型私有化部署：Qwen-0.5B, Phi-3-mini (3.8B)。在 Ollama Q4_0 下，Phi-3 的 TTFT 只有 0.6s，生成速度能达到 15 tokens/s。这已经足够用于简单的客服问答了。
  • 边缘设备/工控机：树莓派 4B + OpenVINO 部署 YOLOv8-Nano (INT8)，FPS 能维持在 2-3 FPS，虽然低但比 CPU 裸跑强百倍。

    • 2. 不适用场景：

  • 高并发实时客服：如果要求响应时间在 50ms 内，CPU 量化绝对做不到（目前最快也就几百毫秒）。
  • 复杂长文本生成：超过 16k context window，Ollama CPU 模式会频繁触发 OOM Kill。

    • 总结与避坑建议

    这次实测证明：无需 GPU 跑 AI 是可行的，但必须做好量化和内核调优。

    我踩过的最大坑就是“盲目追求模型精度”。很多人为了省显存强行上 FP16，结果在 CPU 上跑得比 INT8 还慢。因为 CUDA Core 的并行度优势被完全抹平后，FP16 的计算密度反而成了瓶颈。量化带来的带宽节省远大于计算密度的损失。

    另外，关于环境配置：

  • Python Version: 必须用 Python 3.9 - 3.10 (PyTorch CPU 版本支持较好)。
  • OpenBLAS: 务必安装 Intel MKL 或 OpenBLAS `libomp` 优化版。
  • Model Format: 尽量使用 GGUF，不要自己转 ONNX。GGUF 的量化算法（Q4_K_M）在 CPU 上的兼容性更好，且推理引擎对算子融合支持更成熟。

    • 最后给个建议：如果公司预算允许买一张二手 T4 (16GB)，哪怕只有一张，性能也比纯 CPU 强 50-80 倍。但如果只能有服务器没显卡，Ollama + GGUF Q3/Q4_0 是目前性价比最高的解法。

    不要迷信 GPU，也不要盲目上云。根据业务对延迟的容忍度（P99 Latency）来选型，才是 DevOps 该有的成本意识。
