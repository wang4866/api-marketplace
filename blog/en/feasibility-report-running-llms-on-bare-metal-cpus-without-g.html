Feasibility Report: Running LLMs on Bare Metal CPUs Without GPUs

Title: Feasibility Report: Running LLMs on Bare Metal CPUs Without GPUs

Tags: #CPU-Inference #LLM-DevOps #CostOptimization #llama-cpp

I was tasked to spin up a RAG pipeline with zero GPU budget last week. The stakeholder expected 8B parameter models like Llama-3 or Mistral to run in production on our existing x86 infrastructure without buying new T4s or A10Gs. Everyone said "No way." I decided to test the feasibility of CPU quantized inference using `llama.cpp` and OpenVINO against a vLLM baseline, specifically looking for where this actually works versus where it fails.

This isn't about theoretical benchmarks; this is what happened when we tried Q4_K_M on an Intel Xeon Gold 6230 cluster without touching the GPU card at all. Here are the hard numbers and the specific configuration details I used to make or break the setup.

The Hardware Reality Check: What We Actually Had

We were running off a bare metal instance with two AMD EPYC 7543 CPUs (128 cores total) but only 64GB of RAM allocated per node due to cost constraints. No NVIDIA drivers installed, no CUDA toolkit. Just standard Linux kernel version `5.10.0-24-amd64`.

I expected the throughput would be decent enough for batch processing or low-priority chatbots. The first question was: which quantization format actually matters on CPU? I tested FP32, FP16 (via OpenVINO), and GGUF Q4_K_M using `llama.cpp` version 0.1.89.

The results were immediate. Running the full model in FP32 on this hardware was a disaster—latency spiked to over 5 seconds per token just for initialization, consuming nearly all available RAM bandwidth due to memory paging. Switching to Q4_K_M quantization via GGUF format reduced VRAM usage (well, CPU RAM) by roughly 60% compared to FP16 and cut inference latency significantly.

I ran the following command on a single core affinity setup:

./main -m models/llama-3-8b-Q4_K_M.gguf \
    --ctx-size 2048 \
    --n-gpu-layers 0 \
    --threads 16 \
    --verbose-color

```

The output log showed a Time to First Token (TTFT) of roughly 3.5 seconds. That's slow, but for a non-real-time chatbot handling historical data retrieval, it was acceptable compared to the cost savings. However, when I tried Q2_K quantization to save more RAM, hallucination rates spiked by 18% in math-heavy tasks due to precision loss during attention heads calculation.

The NUMA Affinity Trap: A Real Failure Mode

Here is where things got messy. On a multi-socket server like the EPYC cluster I was using, memory latency varies wildly depending on which CPU socket accesses RAM. By default, `llama.cpp` binds threads to cores but doesn't always respect Non-Uniform Memory Access (NUMA) topology correctly unless configured manually.

I initially ran with `-t 32` without binding. The system load average was high, and inference speed dropped by nearly 40% compared to a single-threaded run on the same model due to cache thrashing across NUMA nodes. I had to fix this using `numactl`.

numactl --cpunodebind=1 \
        --membind=2,3 \
        ./main -m models/llama-3-8b-Q4_K_M.gguf ...

```

After binding the threads and memory to a specific node (Node 0), throughput jumped from 5.2 tokens/sec back up to 7.1 tokens/sec. This is critical for anyone deploying this in production: if you ignore NUMA, your CPU inference performance will be inconsistent across cores. I documented this as `CPU-AFFINITY-ERROR` in our internal runbook after the second day of testing.

Benchmarking Against vLLM (CPU Mode)

We also compared against Open Source LLM serving frameworks like vLLM 0.4.x, which supports CPU inference via PyTorch backend but is notoriously slow without GPUs. I set up a Docker container on an AWS c6i.large instance to test the baseline before switching back to `llama.cpp`.

FROM python:3.10-slim
RUN pip install vllm==0.4.2 --no-binary :all:
CMD ["python", "-c", "from vllm import LLM; llm = LLM(model='meta-llama/Llama-3-8b', device='cpu'); ..."]

```

The startup time alone was 15 minutes to load the model into CPU memory. In contrast, `llama.cpp` loaded in under 90 seconds because it doesn't need CUDA context switching or massive kernel launches for every token generation step. Once warmed up, vLLM (CPU mode) managed roughly 4 tokens/sec, while my optimized `llama.cpp` setup hit 7-8 tokens/sec.

However, the memory overhead was higher in PyTorch-based CPU inference due to tensor fragmentation and Python interpreter overheads. I found that for anything heavier than 13B parameters on a single node without GPU acceleration, vLLM becomes unusable unless you have dedicated RAM allocation per process (which we didn't).

Context Window Limits: The Hidden Bottleneck

I tested the context window size extensively because users expect LLMs to handle long documents. On CPU inference with Q4_K_M quantization, I capped `--ctx-size` at 2048 tokens for stability beyond that. Pushing it higher caused OOM (Out of Memory) errors even though we had enough RAM theoretically; the issue was memory bandwidth saturation rather than capacity.

When running a test file with 16k context on CPU, latency per token increased exponentially after every few hundred generations due to cache misses in L3/L2 hierarchy. The average time jumped from 0.5s (early tokens) to 4.8s (late tokens). This is why I recommend using `--cache-ctx` with a smaller value and relying on external retrieval systems for long documents, rather than trying to force the model context window higher.

The Final Verdict: When CPU Inference Actually Works

After two weeks of testing across three different hardware configurations (Intel Xeon vs AMD EPYC), I can confirm that running AI models without GPUs is feasible under strict conditions:

1. Use GGUF Q4_K_M or Q5_K_M: Anything lower introduces hallucinations; anything higher kills RAM budget on bare metal servers.

2. Bind Threads to NUMA Nodes: Always use `numactl` to prevent cross-node memory latency penalties. I lost nearly half my performance when this was ignored during the initial deployment attempt.

3. Accept Latency Trade-offs: Do not expect real-time chat speeds (10-50 tokens/sec). Expect batch processing or interactive bots where a few seconds of delay is acceptable for massive cost savings.

I stopped using `vLLM` on CPU entirely after version 0.4.x because the Python overhead was simply too high compared to C++ based inference engines like `llama.cpp`. For production workloads, I switched our RAG pipeline to use a hybrid approach: small models (Phi-3-mini) running locally via Ollama with `-n-gpu-layers 0` for quick retrieval queries, and the heavy lifting done on GPU nodes only when necessary.

Lessons from Production Failures

I want to be clear about what didn't work as expected so you don't waste budget:

  • Do not use FP16 quantization: The memory footprint is too high (roughly 2x Q4_K_M) for the marginal gain in accuracy on CPU. It just doesn't fit in RAM without swapping, which kills performance instantly.
  • Avoid PyTorch native inference if possible: Unless you have a specific reason to use ONNX Runtime or OpenVINO, `llama.cpp` remains faster and easier to deploy via Docker for pure CPU workloads due to its lower memory overhead.

    • In summary, running LLMs on CPUs is viable for non-critical tasks like log summarization or document indexing where latency isn't the bottleneck. It saves money but requires careful thread binding and quantization selection. If you need low-latency responses under 200ms per token without a GPU budget, this approach will fail your SLA immediately.
