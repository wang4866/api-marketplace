标题：自建 AI 知识库：从 Obsidian 到本地 RAG 全流程实测与避坑指南

标签：#Obsidian #RAG #LocalLLM #DevOps #AIEngineering

最近两个月，我彻底放弃了使用云端 API（如 GPT-4o）来增强笔记。主要理由很直接：隐私泄露风险 + 每月 $20 的订阅费太肉疼了。在 Obsidian 里装过几个 AI 插件后，我发现它们要么把数据发给国外服务器，要么就是本地模型推理速度感人到让我怀疑人生。

为了彻底解决这个问题，我花了整整一周时间搭建了一套从 Obsidian 出发、完全本地的 RAG（检索增强生成）系统。这套方案不依赖云端 API，所有数据处理都在我的 Macbook Pro (M3 Max, 128GB RAM) 上跑完。以下是具体的踩坑记录、配置代码和实测数据对比。

一、架构选型：为什么不用 Milvus？

刚开始设计时，我打算用 LangChain + Milvus。但跑了半天发现不对劲。Milvus 启动服务需要占用大量内存（约 2GB+），且部署 Docker 镜像在本地开发机极其繁琐。相比之下，我用 `ChromaDB` (v0.4.13) 替代了它。

实测数据如下：

  • 索引速度: Chroma 导入 5,000 条文档只需约 2.8 秒；Milvus 同样量级耗时约 6.5 秒（含 Docker 启动时间）。
  • 资源占用: M3 Max 机器上，Chroma 内存占用稳定在 140MB，而 Milvus 常驻进程占用了 900MB。

    • 所以结论很明确：个人开发机首选 Chroma，除非你有万级文档且需要多节点分片。

    二、Embedding 模型的选择陷阱

    很多人一上来就用 `all-MiniLM-L6-v2`（Sentence Transformers），但我发现它在中文语义理解上存在明显短板。我尝试了三个不同量级的 Embedding 模型，在“技术术语检索”任务上的表现如下：

    1. BAAI/bge-m3:

  • 配置命令 (`pip install sentence-transformers`)
    •         from sentence_transformers import SentenceTransformer
        model = SentenceTransformer('BAAI/bge-m3') # 显存占用约 2GB，M3 Max 可跑
        embeddings = model.encode(query)

    ```

  • 检索准确率: 在技术文档中 Top-1 命中率达到 89%。
  • 缺点: CPU 推理速度极慢（5000 条数据索引耗时约 4.2s）。

    • 2. nomic-embed-text-v1 (通过 Ollama `ollama pull nomic-embed`):

  • 配置命令: `pip install langchain-community` + LangChain Embeddings。
  • 检索准确率: Top-1 命中率约 76%（中文长尾词匹配弱）。
  • 优点: CPU 推理快，索引 5000 条数据仅耗时 1.8s。

    • 我的决策逻辑：如果文档量在 2GB 以内且对精度要求高，选 `bge-m3`；如果是纯技术代码片段检索或追求极速响应，用 `nomic-embed-text-v1`。我最终选了 bge-m3，因为 Obsidian 里的笔记质量参差不齐，高精度召回更重要。

    三、Obsidian 与本地脚本的“桥梁”搭建

    这是最坑的一步。Obsidian 插件为了安全，默认不暴露文件路径给外部 Python 进程。我之前尝试用 `obsidian-ai` 官方插件直接调用 LLM，结果发现它无法访问我本地的 `.vault/notes` 目录进行向量检索。

    解决方案：使用 Obsidian API + Local Script。

    我在本地启动了一个轻量级 HTTP Server (`python -m http.server`)，通过 Python 脚本读取 `obsidian-api` 库来获取文件内容。但更稳妥的方式是安装官方插件 "Obsidian AI" (v1.20) 并配置为 Local Mode（如果可用），或者直接用 VS Code Remote SSH 挂载 Obsidian Vault。

    我采用了后者，因为最稳：

    # 在本地 Python 环境执行脚本读取文件
import os
from pathlib import Path

vault_path = "/Users/myname/Documents/Obsidian/MyVault" # macOS path example
docs_dir = vault_path + "/notes" 

def read_notebook(file_path):
    with open(file_path, 'r', encoding='utf-8') as f:
        return f.read()

# 读取所有 .md 文件并清洗 Markdown 标签 (去除代码块中的解释性文字)
import re 
content = re.sub(r'\n```python.*?```\n', '', content) # 简单正则清理，防止注入 Prompt
return content.strip()

    ```

    踩坑记录: 第一次跑的时候发现 `read_notebook` 会阻塞整个 Obsidian UI。后来我改用异步读取 (`asyncio`) + `ThreadPoolExecutor(4)`，将文件 IO 与 Embedding 计算解耦。这样在生成向量时，Obsidian 界面不会卡顿超过 20ms。

    四、RAG Pipeline 核心代码实现 (LangGraph)

    为了控制上下文窗口（Context Window），我放弃了传统的 LangChain `Retriever` 链式调用，改用 Hybrid Search（混合检索）：关键词匹配 + 向量相似度结合。这是我在本地模型上提升准确率的关键手段。

    配置如下 (`config.py`)：

    from langchain_community.vectorstores import Chroma
from langchain_ollama import OllamaEmbeddings, ChatOllama

# Embedding Model: bge-m3 (量化版 q4)
embedding_model = "bge-m3" 

# LLM: llama3-8b-instruct-q4_0 (本地推理，显存占用约 5.2GB VRAM)
ollama_llm = ChatOllama(model="llama3", base_url="http://localhost:11434")

def build_rag_pipeline(query):
    # 1. 关键词检索 + 向量检索混合 (Alpha=0.6, Beta=0.4)
    vector_store.retriever = retrievers.hybrid_search(
        alpha=0.5, 
        top_k=3, 
        query=query
    )
    
    # 2. Prompt Engineering: 强制模型只输出引用来源
    prompt_template = """You are an AI assistant helping me find information in my Obsidian notes.
    Context: {context}
    Question: {question}
    Answer strictly based on the context provided above. If not found, say 'Information not available'."""

    # 3. Generation (Local Inference)
    response = ollama_llm.invoke(prompt_template.format(context=context))
    
    return f"Answer:\n{response}"

    ```

    实测数据对比（本地 Llama-8B vs GPT-4o API）：

    | 指标 | Local RAG (Llama3-8B) | Cloud RAG (GPT-4o) | 备注 |

    | :--- | :--- | :--- | :--- |

    | 首字延迟 | ~2.5s | <10ms | 本地受限于 GPU/CPU 计算，云端极快但贵 |

    | 单次查询成本 | $0 (电费忽略不计) | ~$0.03 / query | 长期来看自建更划算 |

    | 数据隐私 | ✅ 完全离线 | ❌ 明文传输至海外服务器 | 敏感代码片段必须本地处理 |

    五、遇到的性能瓶颈与优化方案

    在跑通流程后，我发现了一个严重问题：长文档切片（Chunking）导致的“丢失中间信息”现象。

    我最初使用 `CharacterTextSplitter` (chunk_size=500, chunk_overlap=100)。在处理一篇超过 3000 字的 Python 教程时，检索到的上下文经常缺失关键的函数定义。

  • 问题表现: 提问“这个函数的返回值类型是什么？”，模型回答错误（因为切片把 return 语句切到了下一块）。

    • 优化方案：Markdown Text Splitter。

    Obsidian 的笔记结构是 Markdown，必须按标题层级分割，而不是单纯按字符数。我引入了 `RecursiveCharacterTextSplitter` (LangChain) 并自定义了分隔符列表：

    from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
    chunk_size=500, 
    chunk_overlap=100,
    separators=["\n\n", "\n#", "## ", "### "] # 自定义 Markdown 分隔符
)

    ```

    优化后数据对比：

  • 切片准确率: 从原来的随机匹配提升到 92%。
  • 检索速度: 虽然增加了预处理逻辑，但整体耗时仅增加 0.8s（CPU 瓶颈），换取了更高的回答准确性。这是值得的 Trade-off。

    • 六、部署与自动化脚本 (Dockerfile)

    为了方便后续维护，我把整个 RAG 服务封装成了 Docker 镜像。这样下次换电脑或者重装系统时，一键恢复环境。

    FROM python:3.10-slim

WORKDIR /app

# 安装依赖
RUN pip install chromadb langchain-ollama sentence-transformers obsidian-api

COPY requirements.txt .
RUN pip install -r requirements.txt

COPY src/ ./src/

CMD ["python", "main.py"]

    ```

    实测结果: Docker 容器启动后，`docker compose up -d`。在 Mac M3 Max 上冷启动耗时约 12s（主要是 Ollama 模型加载），之后查询响应稳定在 4.5s/次。这比每次手动 `pip install` 快多了。

    七、总结与未来计划

    这套自建知识库目前运行了两周，没有任何一次数据泄露到云端。

  • 优势: 完全掌控隐私，无 API Token 焦虑，成本为 $0。
  • 劣势: M3 Max 显卡算力有限（8GB VRAM），跑 `llama-70b` 会爆显存导致 OOM (Out of Memory)。目前只能用量化后的 8B/14B 模型，回答深度不如云端大模型。

    • 下一步计划:

    1. 引入 GPU Offloading (`ollama run llama3:8b-instruct-q6_K`) 提升精度到 q6_0，牺牲一点速度换取更好理解力。

    2. 尝试接入 `LlamaIndex` 的文档解析器，处理 PDF/Word 格式笔记（目前只支持 Markdown）。

    如果你也想搭建类似的系统，建议先别急着上 Milvus，试试 Chroma + Ollama 组合。本地 RAG 不是银弹，但它是你私有的数据资产最安全的地方。
