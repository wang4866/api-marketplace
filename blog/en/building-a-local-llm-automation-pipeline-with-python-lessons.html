Building a Local LLM Automation Pipeline with Python: Lessons from Production

Title: Building a Local LLM Automation Pipeline with Python: Lessons from Production

Tags: #LLMops, #PythonAutomation, #DevOpsEngineering, #LocalInference

I stopped using OpenAI API for our internal incident triage system last month. The cost was bleeding out of the budget at $0.50 per successful ticket resolution, and network latency added 4 seconds to every single query before a human even saw it. I decided to switch everything to local inference on-premise hardware. This isn't about being "green"; this is about predictability in CI/CD pipelines where we cannot afford the variance of public API rate limits or cold starts.

Here is exactly how I built an automated workflow using Python and a locally hosted LLM, what went wrong during testing, and why you should care about quantization before writing your first line of code.

Hardware Reality Check Before You Start

Don't start by spinning up a massive cluster just to run one script. My baseline hardware is an NVIDIA RTX 3090 with 24GB VRAM running on Ubuntu 22.04 LTS inside Docker Compose for isolation. If you try this without understanding your GPU limits, you will hit OOM errors immediately and waste hours debugging CUDA contexts that don't belong to Python anyway.

I pulled the model using `ollama` because it handles memory management better than raw HuggingFace transformers in a local setup:

docker run -d --name ollama-service \
  -v ./models:/usr/share/ollama/.ollama/models \
  -p 11434:11434 \
  ollama/ollama-server

```

I pulled `llama3.2-3b-instruct` for the initial prototype because it fits in VRAM with a safety margin, but I quickly realized that was too weak for complex code generation tasks. The real production model is `gemma:7b-it`. Here are my specs and performance baseline on this hardware configuration:

  • GPU: NVIDIA RTX 3090 (24GB)
  • Model: Gemma-2B-Instruct-Q4_K_M (Quantized via GGUF)
  • Inference Speed: ~65 tokens/second at batch size 1.
  • Context Window Limit: 8,192 tokens effectively usable before VRAM pressure spikes.

    • The Python Implementation: LangChain vs. Raw Ollama Client

    I initially tried using `langchain-ollama`. It's convenient for chaining prompts together (e.g., Summarize -> Extract Entities -> Generate Action), but I found the overhead was unacceptable. Every time a chain step triggered, it made an HTTP request to localhost:11434. That adds ~50ms latency per hop in your workflow graph.

    I switched to `ollama` Python client directly for production logic. Here is how I structured the agent loop without the abstraction layer bloat:

    from ollama import Client, chat

client = Client(host='http://localhost:11434')
system_prompt = """You are an automated DevOps engineer. 
Your task is to analyze logs and generate a JSON object with 'action', 'command', and 'confidence'."""

response_stream = client.chat(
    model="gemma",
    messages=[{"role": "user", "content": log_input}],
    stream=True, # Critical for real-time UI updates
)

for chunk in response_stream:
    content += chunk['message']['content']

    ```

    Why this matters: Streaming is mandatory. If you wait for the full generation before processing data downstream (like sending a Slack notification), your pipeline stalls waiting on GPU compute time. By streaming, I achieved an end-to-end latency of 3.2 seconds from log ingestion to ticket creation. Without `stream=True`, it took 14 seconds just to get the first token response due to buffering overhead in Python's standard library wrappers.

    The Context Window Trap (A Major Failure)

    I hit a wall during week two when I tried to feed an entire git repository diff into the model context window for root cause analysis. It failed catastrophically.

    The issue wasn't just cost; it was VRAM fragmentation. When `gemma` tries to attend to 16k tokens (equivalent), the KV cache explodes, forcing offloading to system RAM via PyTorch's CUDA allocator fallbacks. This caused latency spikes from ~20ms per token to >800ms per token mid-generation.

    The Data:

  • Context Size: 4K Tokens -> Latency: 15 seconds total generation time.
  • Context Size: 8K+ Tokens (Full Repo) -> VRAM Spike -> Swap Page Faults on CPU RAM -> Generation Time: 2 minutes + Timeout errors in LangChain callbacks.

    • I learned that "Long Context" is a marketing term, not an engineering spec for local inference unless you have A100 GPUs with HBM3 memory. I solved this by implementing recursive text splitting using `RecursiveCharacterTextSplitter` from LangChain before sending anything to the model.

    from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(chunk_size=1500, chunk_overlap=200)
chunks = splitter.split_documents(logs_documentation) # 4 chunks max per request
relevant_chunk = get_relevant_context(chunks)

    ```

    After splitting and filtering relevant logs using a simple keyword search before sending to the LLM, I reduced generation time by 65% while maintaining accuracy. The model stopped hallucinating irrelevant files because it wasn't trying to remember every single line of code from last month's merge request.

    Cost vs. Latency Comparison: Local API vs Cloud Provider

    I ran a benchmark over 7 days comparing the local `gemma` setup against an OpenAI GPT-3.5-Turbo endpoint for our daily ticket volume (approx 200 requests/day).

    | Metric | Local Inference (Gemma Q4) | Cloud API (OpenAI) |

    | :--- | :--- | :--- |

    | Avg Latency | ~18 seconds per request | ~350ms per request |

    | Cost / Request | $0.002 (Electricity only) | $0.04 - $0.06 |

    | Reliability | 99% Uptime (Localhost always on) | Rate limit throttling at peak hours |

    | Data Privacy | Data never leaves network interface | Logs sent to US/EU servers |

    The latency difference is the killer here for local inference, but you can't ignore it if your workflow involves human-in-the-loop verification. If a developer needs feedback in under 10 seconds while they are typing code, waiting 20 seconds for an LLM response feels like watching paint dry. However, for batch processing nightly logs or generating static documentation updates where latency doesn't matter as much as cost and privacy, local inference wins hands down on the ROI side.

    Memory Management Pitfalls in Python Processes

    I made a mistake assuming Docker containers handle memory well by default when running Ollama with LangChain agents inside them. I set `--memory 4g` for my container to save host resources but didn't account for PyTorch's allocator caching GPU context buffers between runs.

    On the first run, it was fine:

    import torch; print(torch.cuda.memory_allocated()) # ~2GB
# ... inference happens ...
print(torch.cuda.memory_allocated()) # 18GB (Cached)

    ```

    By the third consecutive call in a loop without explicit cleanup, I hit `CUDA out of memory` because PyTorch wasn't releasing VRAM properly after streaming finished. The fix was adding an explicit flush and reloading strategy between requests:

    import torch
torch.cuda.empty_cache() # Essential for long-running Python processes with Ollama backend
# Or better yet, restart the ollama container if running as a service every 12 hours to clear state

    ```

    I also had to disable `flash_attention_2` initially because it caused compatibility issues on my specific driver version (CUDA 12.0). I switched back to standard attention kernels until NVIDIA updated their drivers for newer architectures, which improved stability but dropped tokens/sec by roughly 35%.

    Why Not Just Use vLLM?

    You might ask why I didn't use `vllm` instead of Ollama. The answer is simplicity in the Python ecosystem. VLLM requires a separate server deployment and gRPC/HTTP setup that adds another layer of complexity to CI pipelines using GitHub Actions or Jenkins triggers. For our internal tooling, we need "install dependency -> run python script".

    Ollama fits this workflow perfectly because it exposes a standard REST API over localhost:11434 without needing extra Docker Compose files for every new model version I want to test. However, if you are running high-throughput batch inference (e.g., processing 50k lines of logs at once), Ollama will choke on throughput compared to vLLM's tensor parallelism.

    Performance Note:

  • Ollama (Single GPU): ~65 tokens/sec max throughput.
  • vLLM (Multi-GPU Tensor Parallel): Can scale linearly up to 4096 GPUs, but setup complexity is O(N^2) for your DevOps team's maintenance overhead.

    • Final Configuration and Deployment Strategy

    I settled on a hybrid approach where the LLM runs inside a Docker container managed by systemd as `ollama.service`, ensuring it restarts automatically if Python scripts crash due to memory leaks. Here is my final docker-compose configuration that I use in production today:

    version: '3'
services:
  ollama-inference:
    image: ollama/ollama-server:latest
    ports: ["11434:11434"]
    volumes: 
      - ./models:/usr/share/ollama/.ollama/models
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]

    ```

    I also added a `systemd` timer to kill the Python process if it exceeds CPU usage above 80% for more than 5 minutes. This prevents runaway inference loops from burning out our GPU cores during peak deployment times, which happened once when I accidentally sent an infinite loop of prompts without token limits in my LangGraph state machine.

    Conclusion: When to Use Local LLMs?

    You should not build this if you need low-latency responses for chat interfaces or real-time coding assistants where <200ms matters. But if your use case is batch processing, data extraction from private logs, generating synthetic test cases without leaking PII (Personally Identifiable Information) to the cloud, local inference with Python + Ollama/Llama.cpp is viable and cost-effective.

    The main takeaway: Don't optimize for "model accuracy" first; optimize for VRAM efficiency. Quantization isn't just a feature toggle; it's your safety net against hardware failure. I saved $120/month on cloud API costs within the first week of this setup, but more importantly, my team stopped worrying about vendor lock-in and data residency compliance issues when processing sensitive infrastructure logs locally.

    If you are reading this to start building a similar pipeline: Start with `llama3-8b` quantized Q4_K_M on an RTX 3090 or better. Do not use the full FP16 model unless your VRAM is >24GB, because context window expansion will kill your inference speed regardless of how much money you spend on cloud compute credits.
